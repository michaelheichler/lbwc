# Workflow Spawn Protocol

Use this protocol only after the backend resolves to `workflow`, either through a frozen runtime snapshot (`team`, `build`, and Execute mode in `vibe`) or through the solo resolution in step 0 below (`qa`, `fix`, `debug`, `map`, `research`, `init`, and any future ad hoc solo command with no frozen snapshot). Native Agent and native team behavior remain authoritative when the resolution is `in_process`. This backend has no automatic fallback: a requested `workflow` that the capability probe marks unavailable fails closed before any contract or agent exists, and this protocol never substitutes another backend at runtime.

0. **Resolving the backend for a solo, non-team-snapshot command.** Read `.agent_execution_mode` from `<control-root>/config.json`, `.workflow.available` from `<control-root>/claude-capabilities.json`, and `.workflow_execution.enabled` from `<control-root>/config.json`:

    ```bash
    EXEC_MODE=$(jq -r '.agent_execution_mode // "ask"' <control-root>/config.json)
    WORKFLOW_AVAILABLE=$(jq -r '.workflow.available // false' <control-root>/claude-capabilities.json 2>/dev/null || echo false)
    WORKFLOW_ENABLED=$(jq -r '.workflow_execution.enabled // false' <control-root>/config.json 2>/dev/null || echo false)
    RESOLVED_BACKEND=in_process
    ```

    When `EXEC_MODE` is `workflow`: stop before any contract or agent exists and report `.workflow.unavailable_reasons` verbatim when `WORKFLOW_AVAILABLE` is not `true`. There is no automatic fallback from a requested `workflow`. Otherwise, when `WORKFLOW_ENABLED` is not `true`, stop with `workflow backend is disabled in configuration`. Otherwise set `RESOLVED_BACKEND=workflow`.

    When `EXEC_MODE` is `ask` and both `WORKFLOW_AVAILABLE` and `WORKFLOW_ENABLED` are `true`, ask one bounded question before any contract or agent exists, following `references/ask-user-question.md`, with a command-specific header, question, and `Cancel {noun}` label, offering exactly `Workflow run`, `Native spawn`, and `Cancel {noun}`. On `Workflow run`, set `RESOLVED_BACKEND=workflow`. On `Native spawn`, keep `RESOLVED_BACKEND=in_process`. On `Cancel {noun}`, stop, no contract or agent exists.

    Any other `EXEC_MODE` (including `in_process` and `tmux`, which these commands do not run through a pane group), or `EXEC_MODE=ask` when `WORKFLOW_AVAILABLE` or `WORKFLOW_ENABLED` is not `true`, keeps `RESOLVED_BACKEND=in_process` without asking. The shipped default has `workflow_execution.enabled=false`, so an `ask`-mode run on an unconfigured project proceeds silently on `in_process` rather than offering an option that would only dead-end on `workflow backend is disabled in configuration`.

    This step is a fast, friendly stop before any contract or agent work happens. It is not the only gate: `workflow-generator.sh` independently re-validates `.workflow.available` and `workflow_execution.enabled` at generation time, re-reading `CLAUDE_CODE_DISABLE_WORKFLOWS` and `CLAUDE_CODE_SUBAGENT_MODEL` live from the environment, and fails closed even if this step is skipped or misjudges a stale catalog.

1. Confirm `claude-capabilities.json`'s `.workflow.available` is `true` before resolving the backend to `workflow`. Availability already accounts for the version floor, `disableWorkflows`, `CLAUDE_CODE_DISABLE_WORKFLOWS`, and an active `CLAUDE_CODE_SUBAGENT_MODEL` override. `.workflow.unavailable_reasons` names every gate that failed. A stale probe from a config-only path is not a substitute for this check. Two shell layers enforce this regardless of what step 0 or a frozen snapshot conclude: `scripts/runtime-snapshot.sh` enforces it on every `freeze` and `validate` call for a requested `workflow` backend, and `scripts/workflow-generator.sh` enforces it again immediately before every generation, reading `.workflow.available` from the control root's `claude-capabilities.json` and `workflow_execution.enabled` from its `config.json`, and failing closed with the unavailable reasons printed verbatim when either gate is not met. `CLAUDE_CODE_DISABLE_WORKFLOWS` and `CLAUDE_CODE_SUBAGENT_MODEL` are re-read live from the current session's environment at the moment of that call, not only from the last `claude-capabilities.sh refresh`, so a variable set after that refresh still fails closed instead of freezing on stale data. This is a shell-level gate, not only a protocol instruction to follow, and it applies to every caller including a solo command that never builds a frozen snapshot.
2. Issue the same schema 3 task contract used by the native and tmux paths, with `--requested-backend workflow --resolved-backend workflow`. Generate every roster definition with `--execution-backend workflow`, exactly as the native and tmux paths generate theirs. Reject generator metadata that disagrees with the snapshot or, for a solo command, with `RESOLVED_BACKEND`.
3. Run `workflow-generator.sh <solo|pair|trio> <role> --contract <path> --task-id <id> ...` while the contract is still `planned`. It requires that state and rejects anything else. It renders `templates/workflows/<shape>.js.tpl` into `<control-root>/workflows/<contract-id>.js`, checks the rendered file against the roster and the forbidden-token rules, registers it in the workflow manifest, and prints a `Workflow-call parameters:` block giving the path and digest, followed by a `WORKFLOW_READY <task-id>` line. `contract_id` and `task_identity` are distinct fields: the file name uses the contract id, the printed line names the task id.
4. Transition the contract to `dispatched` only after the workflow script is registered.
5. Call `Workflow` exactly once, passing only `scriptPath` from the generator's own output. Never pass `script`, and never transcribe or paraphrase the rendered file's contents into the call. The `PreToolUse` guard on `Workflow` (`scripts/workflow-spawn-guard.sh`) independently re-hashes the path against the registered digest and denies an inline `script`, an unregistered path, a tampered digest, or mismatched `args`. A denial is a stop, not a trigger to try another backend.
6. `Workflow` launches the run in the background. Its own tool result reports only the launch (`taskId`, `runId`, `transcriptDir`, `scriptPath`), never the run's outcome. Do not treat that result as the roster's report.
7. Inside the run, every `agent()` call the template makes resolves to a generated `lbwc-` definition. The hooked `agent_type` on that subagent's own tool calls is the generated name, exactly as it is for a native or tmux teammate. `test_scope_guard.py` and `skill_gate.py` enforce role scope from that same field without any change. Entry is not simultaneous the way native admission is. `references/agent-spawn-protocol.md` requires every admitted member spawned in one message, so a native or tmux pair or trio reaches `running` together. `templates/workflows/pair.js.tpl` instead awaits the engineer's `agent()` call before starting the critic's, and `templates/workflows/trio.js.tpl` awaits engineer, then `test-dev`, then critic, in that order. A workflow pair or trio therefore has at most one member `running` at any moment, entering `running` one member at a time in template order. The `state ... running` transition is driven by the first admitted member reaching `running`, never by waiting for every admitted member to reach it.
8. The run ends with a top-level `return`, not a `log()` call. `log()` output populates the run's `logs` and never carries the final result. Read the terminal `result` once the run completes. A `user_decision_required` result is the only path back to the user: ask exactly one bounded `AskUserQuestion` about continuing remediation, following `references/ask-user-question.md`. Any other terminal result is the roster's report.
9. There is no pane, session, or bus to clean up. The run's own transcript directory and `wf_*.json` state are session-scoped. No explicit teardown call is part of this protocol.
