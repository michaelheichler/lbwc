# Designing for Different Needs

Source: About Face: The Essentials of Interaction Design, 4th Edition (Cooper, Reimann, Cronin, Noessel, 2014), Chapter 16.

## In one line

Serve the full range of user skill levels, preferences, languages, and abilities by offering redundant command paths, a learnable route from beginner to expert, and inclusive defaults, rather than designing one interface and hoping it fits everyone.

## Core ideas

**Users move through skill stages.** Most people start as beginners, quickly become "perpetual intermediates" who know their own working set of commands but never bother mastering the whole app, and a small number become experts. Design should optimize for perpetual intermediates while still giving beginners an on-ramp and experts full power, because assuming everyone will become an expert (or stay a beginner) misreads how people actually use software.

**Command modality is the lens for skill level.** Every way of issuing a command falls into one of three modes:
- Pedagogic: menus, dialogs, labeled controls that teach through inspection. Best for beginners because the interface explains itself.
- Immediate: direct manipulation, sliders, buttons, toolbar icons that act on data right away with no intermediate step. Suits users who already know what they want.
- Invisible: keyboard shortcuts, gestures, swipes with no visible trace in the UI. Fastest, but must be memorized, so it serves intermediates and experts only.

Why it matters: an interface that only offers one modality forces either constant hand-holding for experts or an impossible learning curve for beginners. Offering multiple modalities for the same command lets each user self-select their own path, and mobile's cramped screen real estate is exactly why tours and overlays exist to substitute for missing pedagogic space.

**Norman's information in the world vs. information in the head.** Pedagogic commands rely on information in the world (the interface tells you what to do, slower but reliable). Invisible commands rely on information in the head (memorized, fast, but forgettable and requires upkeep). Immediate commands sit in between. Recognizing which one a control demands tells you who it will work for.

**Memorization vectors move users up the skill ladder.** A memorization vector is the path by which a user discovers the faster immediate or invisible equivalent of a pedagogic command they already know (for example seeing "Ctrl+S" next to "Save" in a menu). Vectors buried in documentation or help text are nearly useless because they demand the user go looking before they know there's something to find. Vectors embedded directly in the interface (menu accelerators shown inline, icons repeated everywhere the function appears) work because they're seen passively during normal use and only registered once the user is ready to notice them. Mobile platforms mostly lack this mechanism, which is why first-run tours substitute for it.

**The working set explains what to make fast.** A working set is the subset of commands an individual user has memorized through repetition. It differs person to person but overlaps heavily within a persona. The overlapping core across most users is the minimal working set. Because these commands get used constantly, they should get the fastest (immediate) modality by default, and the interface should let other commands be "promoted" to immediate access as an individual's personal working set grows. Any command with immediate modality still needs a pedagogic twin somewhere so beginners can discover it. Exception: dangerous, hard-to-reverse commands (Erase All, Abandon Changes) should be deliberately kept out of easy immediate reach and tucked into menus and dialogs, in line with the "hide the ejector seat levers" principle from Chapter 11.

**Contextual help beats interruptive help.** The best help arrives at the point of need without breaking the user's flow. This is why in-context patterns (tours, overlays, hints, tooltips) exist alongside traditional reference help, and why each is scoped to a different moment in the user's journey.

**Full-text search is not a substitute for a hand-built index.** Search only finds what matches the literal wording in the help text, but users think and phrase problems in their own mental model's language ("turn this cell black" versus "set shading to 100 percent"). A synonym-rich index, built by someone who understands the app's functions (not just its help text), captures those mismatches. The index is as important as the help content itself, because a user forgives bad prose more readily than an apparently missing answer. When indexing is this hard, it can be cheaper to fix the interface's learnability than to build a great index.

**Help entries need overviews, not just mechanics.** Telling a user what a command literally does ("lets you enter macros") answers nothing. A good help entry states scope, effect, power, upside, downside, general process, and comparison to alternatives, so the user can decide whether and how to use the feature.

**Personalization and configuration are different problems with different audiences.** Personalization is decorating persistent objects (colors, themes, fonts) without moving them. It satisfies an emotional and ownership need and does not hurt navigation. Configuration is moving, adding, or removing persistent objects (rearranging toolbars, menus). It helps expert users and IT-managed environments but actively hurts navigation for everyone else if done carelessly, because it destroys the spatial memory users build around fixed layout. Design personalization tools to be simple, previewable, and trivially reversible (a "restore defaults" is mandatory).

**Idiosyncratically modal behavior needs both options, not a compromise.** When usability testing reveals a population evenly split on which of two interaction idioms they prefer, don't pick a winner and don't try to average the two. Support both simultaneously so each user's preferred behavior "just works" without a settings toggle. Classic example: Windows menus support click-and-drag, click-then-move-then-click, and click-and-drag-across-menus, all layered on the same menu bar without conflict.

**Wizards trade user control for guaranteed completion, at a cost.** A wizard forces a strict question-by-question sequence to configure something. This violates "provide choices rather than ask questions" and tends to devolve into a click-Next ritual where users stop critically engaging, especially when questions expose raw implementation details (like asking for an IP address) instead of being reframed in user terms. Wizards are legitimately appropriate for (1) one-time hardware or device setup and activation handshakes, and (2) survey-style data collection where a sequence of questions is the actual task. Everywhere else, a better pattern is a smart automatic default (based on past behavior or good defaults) that the user can then adjust with normal tools, essentially a smarter version of a gallery or template rather than an interrogation.

**Localization vs. globalization are different design problems.** Globalization means building one interface that works across cultures and languages. Localization means translating and adapting it per locale. Immediate, icon and gesture-driven idioms globalize easily since they're visual, not textual, but symbols and colors still carry unintended cultural meaning (an X in a checkbox reads as "deselect" in Japan, not "select") and must be checked. Pedagogic, text-heavy idioms (menu labels, tooltips, hints) must be localized through translation, and translation has to be reviewed holistically. Individually-correct translations can still produce an incoherent whole when items appear together (a menu, a dialog), so check the full assembled surface, not just isolated strings. Practical localization landmines: text length varies a lot by language (German and Spanish routinely run longer than English, which breaks tight mobile layouts), some scripts don't alphabetize the way Latin scripts do, date, time, number, and currency formatting conventions differ by country, and some locales use non-Gregorian calendars or week numbers.

**Accessibility is inclusive design, not a special mode bolted on.** Accessible design serves people with cognitive, sensory, or motor impairment (from age, accident, or illness) and non-impaired users simultaneously. The World Health Organization estimated roughly 750 million people worldwide have some disability at the time of writing, yet accessibility is routinely neglected. A product counts as accessible when users, impaired or not, can perceive and understand all instructions, information, and feedback, can perceive, understand, and manipulate all controls and inputs, and can navigate with constant awareness of where they are. These conditions don't all have to be met by a single interface presentation. A separate accessibility mode or option set (contrast, text size, screen reader) is an acceptable strategy.

**Consider an accessibility persona.** Add an accessibility-focused persona to the persona set during research, ideally grounded in real interviews with people whose disabilities affect product use. A provisional persona is an acceptable fallback if that isn't possible. It's normally a secondary persona (shares a primary persona's goals, plus extra needs to accommodate without degrading their core experience), but occasionally making it primary produces breakthrough general-purpose design, the way OXO's Good Grips kitchen tools were designed for users with arthritis and turned out to be better for everyone.

## Named patterns and principles

- **Command modalities (pedagogic, immediate, invisible)**: the three ways users can issue commands. Use pedagogic for onboarding and discovery, immediate for confident repeat use, invisible for speed once memorized. Works because it matches interface behavior to how far along the skill curve a user is.
- **Information in the world vs. information in the head** (Norman): a lens for whether a command's knowledge lives in the interface (world) or in the user's memory (head). Use it to predict who a given command modality will actually work for.
- **Memorization vector**: the in-interface path (inline accelerator labels, repeated icons) that teaches a user the faster equivalent of a command they already know pedagogically. Put vectors in the interface itself, not documentation or help, because users only notice them once they're ready and don't need to go looking.
- **Working set / minimal working set**: the commands an individual (or the shared core across most users) actually uses regularly. Give the minimal working set immediate modality by default and let users promote more commands into their own working set. This keeps frequent actions fast without bloating the default UI.
- **Hide the ejector seat levers** (referenced from Chapter 11): dangerous, hard-to-undo commands should not get easy immediate or invisible triggers. Keep them behind a deliberate menu or dialog step so they can't be triggered by accident.
- **Guided tours**: a short (five to seven screens max) sequential set of cards or screens shown on first run (or major update) that demonstrate function and behavior, not collect input like a wizard does. Must include a skip button on every screen and a way to relaunch later. Use for apps whose function isn't self-evident from the UI alone, especially mobile where pedagogic space is scarce.
- **Overlays**: a transparent annotation layer over the live interface pointing out key controls with brief text, shown on first run and relaunchable later (settings menu or a small help icon). Use for relatively simple apps where a full tour is overkill, and can be combined with a tour's sequential swipe-through structure (as Zite does).
- **Galleries and templates**: pre-built starting points (document templates, shape stencils) that users can pick and then customize, instead of forcing everyone to build from a blank slate. Use in any authoring tool. Blank slates intimidate most users, and this respects that some users want atomic tools while others want a head start.
- **Input and content area hints**: light placeholder text inside empty fields or a whole empty content area, disappearing once the user engages, sometimes paired with one-time inline configuration controls. Use to fill dead empty space with just-in-time guidance instead of leaving it silent.
- **Wizards**: a Microsoft-originated pattern of step-by-step dialogs collecting configuration input in sequence. Appropriate for one-off hardware or device setup and for surveys. For nearly everything else, prefer a smart automatic default the user can edit afterward, because wizards violate "provide choices rather than ask questions" and train users to blindly click Next.
- **Provide choices rather than ask questions** (referenced from Chapter 11): named as the principle wizards typically violate. Present sensible pre-made options instead of interrogating the user with raw configuration questions.
- **ToolTips and ToolTip overlays**: modeless hover-triggered labels on desktop (natural because it mimics a person pointing while explaining). On mobile, where hover doesn't exist, a tap-triggered modal batch of all tooltips at once substitutes. Best treated as a "cheat sheet" for complex authoring apps, not as a first-run welcome experience.
- **Personalization vs. configuration**: personalization decorates persistent objects (color, theme, font) without moving them and helps navigation and ownership. Configuration moves, adds, or removes persistent objects and can hurt navigation if the user isn't the one driving it. Offer personalization broadly and easily (with instant preview and one-click revert to defaults). Offer configuration mainly to experts and IT-managed deployments who need it.
- **Idiosyncratically modal (behavior)**: when a user population splits roughly evenly on which of two interaction styles they prefer, support both concurrently rather than picking one. Works because forcing a single choice always alienates roughly half of users for no real gain.
- **Full-text search vs. indexing**: full-text search only matches literal wording, a curated index mapped to users' own mental-model phrasing catches what the raw text can't. Build the index by studying the app's functions, not just its existing help copy.
- **Overview descriptions**: help content should open by stating scope, effect, power, tradeoffs, process, and comparative context for a feature, not just restate its literal function. Needed because users are trying to decide whether and how to use something, not just parse a definition.

## How to apply

- Offer at least two command modalities (pedagogic plus immediate or invisible) for every important function, except dangerous or destructive ones, which should stay pedagogic-only and out of easy reach.
- Put memorization vectors inline in the UI itself (accelerator text on menu items, matching icons across menu, toolbar, dialog, and help), not only in docs or help text.
- Identify each persona's minimal working set from research or usage analytics, and give those commands the fastest modality by default. Provide a mechanism for users to promote additional commands into immediate access as their personal working set grows.
- For first-time and unfamiliar-feature onboarding, use a short guided tour (max 5-7 screens, skippable, relaunchable) or a lightweight overlay, sized to the app's complexity. Don't build a wizard for this unless it's genuine one-time device or service setup, or a survey.
- Design help content around the user's own phrasing of their problem, not the literal feature name. Invest in a synonym-aware index built by someone who knows the whole feature set, and open each help entry with an overview (scope, effect, tradeoffs), not a restated definition.
- Separate personalization controls (safe, easy, instantly previewable, one-click reset to default) from configuration controls (reserved for advanced or expert users and admin-managed deployments), because moving persistent layout elements can break other users' navigation.
- When usability research shows a population split roughly evenly on an interaction preference, implement both behaviors concurrently instead of forcing a single choice or adding a settings toggle.
- Treat globalization (visual, icon and gesture-based, culturally-checked idioms) and localization (translated text, reviewed holistically as assembled screens, not string by string) as separate design passes. Account for text-length variance, non-Latin sorting, and date, number, and calendar format differences up front.
- Build an accessibility persona into the persona set (ideally from real interviews with users who have relevant disabilities) and design against the three accessibility goals: perceivable instructions and feedback, perceivable and operable controls, and consistent navigational awareness.
- Follow the 10-point accessibility checklist below for any app with a meaningful user base of impaired users (nearly all consumer and enterprise apps, especially anything aimed at seniors or people managing illness): use the OS's own accessibility tools and guidelines, don't override user-selected system settings, enable standard keyboard access methods, add display options for those with limited vision, provide visual-only and audible-only output, don't flash, flicker, or blink visual elements, use simple clear brief language, use response times that support all users, keep layouts and task flows consistent, and provide text equivalents for visual elements.

## Watch out for

- Don't rely on documentation or a help system as the sole path to discovering faster (immediate or invisible) commands. Users won't go looking for what they don't know exists.
- Don't assume mobile apps can skip memorization vectors just because there's no room for them. Use first-run tours and overlays to compensate, since the platform itself provides little native mechanism for this.
- Don't let a wizard become a substitute for actually designing the feature. Asking a user for an IP address inside a wizard is exactly as confusing as asking outside one. "We'll make it easy with a wizard" is the same abdication as "we'll document it in the manual."
- Don't confuse configuration with personalization: moving persistent UI elements (not just re-skinning them) can break navigation for the user and for anyone else who relies on consistent layout.
- Don't try to satisfy a genuinely split user preference with a single compromise design. That satisfies neither side. Support both idioms.
- Don't index only the words that appear in your help text. Users describe problems in their own mental model's terms, and a full-text search alone will miss them.
- Don't use color as the only carrier of meaning. Pair it with shape, position, size, brightness, or text labels so color-blind and low-vision users aren't excluded.
- Don't flash, flicker, or auto-scroll visual elements faster than about 2 Hz. Beyond usability annoyance, it can trigger seizures in people with epilepsy or other brain disorders.
- Don't hard-code short timeouts on user actions unless there's a real reason (such as security). If a timeout is unavoidable, make its duration user-adjustable, and default any adjustable response-time setting to roughly 10x your app's average, including how long transient notifications stay visible.
- Don't override OS-level or user-selected accessibility settings (color scheme, font size and weight, input device behavior) with your app's own hard-coded defaults.
- Don't leave purely visual controls untagged. Screen readers and text-based browsers need text equivalents for every visual element to be usable at all.
