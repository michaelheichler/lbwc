# Designing for the Desktop

Source: About Face: The Essentials of Interaction Design, 4th Edition (Cooper, Reimann, Cronin, Noessel, 2014), Chapter 18.

## In one line

Desktop software is built from a small vocabulary of window, menu, toolbar, pointer, and direct manipulation idioms, and the designer's job is choosing which idiom fits which task, then executing the mechanical details (thresholds, feedback, timing) that make it feel effortless.

## Core ideas

**Windows are rooms, not just containers.** A sovereign application's primary window holds content plus navigation and control panes. Secondary windows (dialogs, detached palettes) support it. Treat every extra window like adding a room to a house: only build one if an existing room genuinely cannot serve the purpose. The reasoning is goal-directed, not function-directed: developers naturally think in discrete functions and give each one a dialog, but users think in goals, and constant trips to a "separate room" for tightly-coupled work (adjusting brightness while editing a photo) breaks their flow and hides the thing they actually care about (the image itself).

**Match window strategy to how users share data across documents.** MDI (one app instance holding many document windows) trades performance for the convenience of juggling closely related views (a set of mockups). SDI (one app instance per document) is simpler and preferred in most modern software, but forcing every workflow into SDI is wrong when users need several related views open in one context (an invoice next to a vendor history). MDI's own internal window management (minimizing, maximizing, or tiling document-windows-within-a-window) doubles the window-management excise if implemented naively. Prefer clean document tabbing or transitions instead.

**Overlapping windows solve a real problem badly at scale.** They mimic a physical desk (pull a paper to the top to work on it), but a small screen isn't a big desk. A stray click can bury an app, and users may re-launch an app they think they "lost". Tiling divides screen real estate evenly and simplifies navigation, but wastes pixels and was rejected as a default consumer idiom (though remnants persist: "show windows side by side," Windows 8 tiles). Virtual desktops multiply screen space for power users who run many apps at once, but don't solve the core problem for typical users. Full-screen, one-app-at-a-time modes (helped by task switchers or docks) are the pixel-friendly, low-confusion trend, especially as tablet and phone habits bleed into desktop.

**Multipaned windows are the best of both worlds for sovereign apps.** Independent panes sharing one full-screen window (Outlook's mailbox list, message list, reading pane, and calendar) deliver related information together with almost no navigation or window-management excise. For any sovereign app of real complexity, multipane layout is close to mandatory. A common effective split: one pane for navigation or building blocks, an adjacent pane for viewing or construction. Stacked panes (tabs, Excel-style sheet tabs) are a related pattern, common in dialogs and increasingly in sovereign windows and browsers.

**Window states are minimized, maximized, and the awkward third state.** The third state (windowed, sharing the screen with icons and other windows) doesn't even get a real name from Apple or Microsoft ("restored" or "pluralized"). Sovereign apps normally live maximized or full-screen, with little reason to run them windowed except to drag data between apps. Transient apps (calculator, IM, file browser) are naturally windowed.

**Menus exist to teach, not to be fast.** Because most everyday functions are no longer performed primarily through menus, the menu's real job is pedagogical: scanning menu titles and items tells a new user the scope and power of the application, the way scanning a restaurant's posted menu tells you what kind of place it is. This has direct wording consequences: menu items should be verbose enough to explain themselves ("Open Report," not "Open," and "Auto-arrange icons," not "Auto-arrange"), and should avoid jargon the user hasn't learned yet. Since teaching is the point, terseness is the wrong goal for menu text, and nearly every function should appear somewhere in the menus so it can be discovered and learned, even if it is rarely invoked that way.

**Menus should carry redundant teaching signals.** Disabling (graying out) inapplicable items, showing check marks for on and off state, showing the same icon used on the corresponding toolbar button, and displaying keyboard accelerators next to commands, all let users absorb information passively (subconsciously) until they're ready to use it, at which point it's already familiar. A global Undo and Cancel buttons on dialogs let users experiment with menu items without fear, which is itself part of the learning environment.

**Check marks beat flip-flop menu items.** A flip-flop item that alternates its own label between two states ("Display Toolbar" / "Hide Toolbar") is ambiguous: is it offering an action or describing current state. A single item with a check mark that toggles is unambiguous, showing state and offering the toggle in one control.

**Accelerators need three disciplines.** Follow platform standards (Ctrl+C, Ctrl+V, Ctrl+P, Ctrl+S) so users' existing habits transfer. Triage the full function set into "everyone uses this daily" (must get an accelerator), "nobody uses this daily" (must not), and an ambiguous middle group you triage again, giving the best remaining keys (F2, F3...) to the most useful survivors and obscure combinations (Alt+7) to the rest. Always display the accelerator next to the menu item, or nobody discovers it. Where possible, pick the key by the command's first letter (Ctrl+C for copy) so it's memorable. Consider making accelerators user-configurable for expert or sovereign use, with a Return to Defaults escape hatch.

**Access keys (mnemonics) are not optional polish.** They give a full keyboard path through every menu (Alt engages mnemonic mode, arrow keys navigate, the underlined letter executes) and should be complete, especially in text-heavy applications, because your most experienced users will lean on the keyboard and abandon software that fights them for it.

**Cascading (hierarchical) menus are hard to use and mostly obsolete.** They require precise two-dimensional mouse movement and make command sets hard to browse (tracing a path through a multilevel Start menu is like tracing a maze). Modern high-resolution menu bars can fit an app's whole function set into roughly half a dozen one-word top-level groups, each roomy enough for its own items, so a deeper level is rarely needed. The dialog box (not a submenu) is the right container for a command's sub-choices. If you must use cascading menus, reserve them for rarely-used functions in sophisticated sovereign apps, and give the submenu a wide movement threshold so it doesn't vanish when the cursor wobbles.

**Toolbars and menus divide labor by user maturity.** Menus are complete, teach beginners, and hold seldom-used advanced functions. Toolbars are modeless, always-visible, single-click, and serve frequently-used commands for the "perpetual intermediate" (the majority of real usage over an app's lifetime). Don't think of a toolbar as merely a faster menu, think of it as a dedicated home for the small set of things almost every user does constantly.

**Toolbars beat modeless dialogs for persistent tool access.** Both are modeless, but toolbars are visually distinct from dialogs (no ambiguity about what they are), never need to be dismissed, and are far more screen-space-efficient while not covering the content they operate on. Docking toolbars (drag off the edge to float, drag back to re-dock) combine the space efficiency of docked toolbars with the positional flexibility of floating windows.

**Icon buttons are recognition aids for people who already know the app, not teaching devices for newcomers.** Inventing a "perfect" visual metaphor for first-time comprehension is largely a lost cause (metaphors are inherently limited). The icon's real job is to be quickly distinguishable from its neighbors once learned, with menus (via matching icons) carrying the teaching load. Because pairing text labels with every icon burns too much screen space, ToolTips solve this by lazily surfacing the label only after a deliberate hover pause, teaching intermediate or infrequent users without visually spamming everyone else.

**Toolbar controls should disable, not disappear, when inapplicable.** Removing controls when they don't apply shifts other controls' positions, and users memorize toolbars by spatial position. A toolbar whose layout shifts unpredictably becomes distrusted and disorienting.

**Toolbars grew beyond icon buttons into a full control surface**: combo boxes (font and style pickers that also show current state), dropdown menus embedded in a toolbar button (Undo history), and buttons whose state reflects data (an italic button that shows whether the current selection is already italic). Ribbon controls (Microsoft Office 2007+) fuse menu and toolbar into a single tabbed, labeled, heterogeneous control surface, trading some screen space for a hybrid of teaching and speed.

**Toolbars default to a "best guess" set and let power users customize.** Shipping every plausible function on the default toolbar dilutes it with things most users rarely touch. Personas and scenarios are the right tool for deciding what belongs in the default set. Customization is valuable for power users, and in practice people rarely wreck their own toolbar setup badly, they make small incremental changes over time.

**Tool palettes are not toolbars.** Toolbar controls act on the current selection. Tool palette controls are mutually exclusive operating modes (only one tool active at a time: creation, selection, manipulation modes), historically vertical with two columns of icon buttons, and usually indicate the active mode via a cursor change. Palettes and toolbars both support docking and floating.

**Sidebars (task panes) replace dialog-box functionality with modeless, always-present panels.** They minimize screen-management excise further than palettes, since the user typically can't undock or dismiss one at a time (only hide the whole sidebar), removing per-panel positioning chores. Drawers (panels stowed offscreen, popped open on demand) trade screen space back for some of that excise, and can be a reasonable compromise on small screens. Letting power users hide and restore all secondary panes with one keystroke is a good way to reclaim focus without losing the sidebar model's benefits.

**Mouse interaction has a hard seam between fine and gross motor control.** Near moves keep the heel of the hand planted and use finger muscles. Far moves require lifting the hand and using arm muscles. Switching between these mid-task (as classic scrollbars force, with the up-arrow, thumb, and down-arrow spread across the whole bar) is effortful and should be minimized by placing related controls together. Touch typists especially resent being pulled off the keyboard to the mouse and back, so keyboard equivalents matter for productivity software, and every mouse idiom should ideally have a non-mouse alternative for users who find precise pointing, clicking, or double-clicking difficult.

**Mouse-down and mouse-up carry distinct meanings, and getting this backwards breaks the interface's escape hatches.** Over selectable data, mouse-down selects (because a drag might follow, and you can't drag before selecting). Over a control, mouse-down only proposes the state change (tentative activation), mouse-up commits it. This lets a user back out of an accidental click by dragging off the control before releasing.

**Right-click and the context menu took years to be treated as first-class.** Apple's single-button-mouse research optimized for beginners at the expense of the intermediate and expert majority who benefit from direct object-scoped context menus. Microsoft mainstreamed the pattern with Windows 95 after Borland pioneered it, and Apple eventually followed.

**Selection is the concept that plugs the gap object-verb interfaces need.** English usually phrases commands verb-object ("throw the ball"), and command lines mirror that. GUIs mostly use object-verb order instead ("select the ball, then throw it") because verb-first requires the system to track an open-ended, unterminated list of objects still to come, a clumsy stateful negotiation. Object-verb order sidesteps that (no termination problem, commands can be shown contextually based on what's selected, lowering cognitive and visual load), at the cost of introducing "selection" as a new intermediate concept the user must learn, though it maps naturally onto everyday nonlinguistic action (pick up the can, then use the opener). Verb-object order is still better when the object can't reasonably be enumerated up front (address lookups in mapping software). Dialogs, which resolve their own object list via an OK button, don't need selection to function the same way.

**Discrete vs. contiguous data drive different selection rules.** Discrete objects (icons, drawing shapes) have no inherent order, so users reasonably want to multi-select non-adjacent items (Ctrl+click). Contiguous data (text, spreadsheet cells) has a meaningful sequence, so non-contiguous multi-selection is rarely worth the visualization and accidental-operation risk it creates. Contiguous interfaces should support extending a selection (Shift+click) rather than disconnected picks.

**Mutual exclusion is the default, additive selection is the deliberate exception**, almost always gated behind a modifier key (Ctrl for discrete additive selection, Shift for contiguous extension in most Windows conventions). Mixing these conventions inconsistently within one control type (some list or file views use Ctrl for "normal" additive but Shift to extend as if it were contiguous) creates confusion.

**Group selection via drag rectangle** ("rubber-band select"): clicking empty space between discrete objects and dragging defines a rectangle, and anything wholly enclosed when the button is released gets selected as a group.

**Selection needs to be visually bold, unambiguous, and not color-dependent** (a meaningful fraction of users are color-blind). Historic inversion is striking but reads poorly in full-color UIs. Alternatives include colored backgrounds, outlines, pseudo-3D depression, and handles. For visually busy content (photographs, artwork) where any static visual property change might get lost, animated selection indicators ("marching ants"/marquee, a moving dashed outline) work regardless of underlying color.

**Insertion points are a special selection state for contiguous data**: rather than selecting an element, the selection can mark the empty space between two elements (a text caret), and typed or pasted content replaces whatever contiguous selection currently exists (an insertion point is the degenerate, zero-width case of that). Discrete selections instead hand incoming data to the selected object, which may replace itself or interpret the data in an object-specific way.

## Named patterns and principles

- **WIMP** (windows, icons, menus, pointer): the founding vocabulary of GUI desktop computing, established at Xerox PARC and inherited by the Mac and Windows.
- **"The utility of any interaction idiom is context-dependent."** No idiom (MDI vs SDI, tiling vs overlap) is universally correct. Choose based on the actual task and how users relate documents to each other.
- **"A dialog box is another room, have a good reason to go there."** Treat every secondary window as a real cost to the user's flow, justify it by goal-fit, not developer convenience.
- **"Provide functions in the window where they are used."** Functions tightly coupled to the primary task (adjusting a photo's brightness while editing it) belong in the main window or pane, not a dialog, even though segregating them looks natural from a code-organization point of view.
- **Unnecessary rooms vs. necessary rooms**: functions used constantly and intimately tied to the current goal (drawing tools) belong integrated in the main workspace. Functions used outside the normal flow, or requiring separation for propriety, safety, or rarity (a database purge, importing clip art), rightly belong in a separate dialog or facility. Decide by examining the user's actual goal sequence, not by the developer's functional decomposition.
- **"Use menus to provide a pedagogic vector."** Menus' primary value today is teaching scope and capability, not raw execution speed.
- **"Disable menu items when they are not applicable."** Graying out inapplicable items teaches users the current context's boundaries.
- **"Use consistent visual symbols on related commands."** Reuse the same icon on a menu item and its corresponding toolbar button so each idiom reinforces the other's learnability.
- **Check-mark menu item vs. flip-flop menu item**: use a single toggled check-mark item, not an item whose label swaps between two competing action phrasings, to avoid "is this an action or a state" ambiguity.
- **"Toolbars give experienced users fast access to frequently used functions."** Toolbars are a distinct idiom from menus, not a shortcut layer on top of them.
- **"Use ToolTips with all toolbar and iconic controls."** A well-timed hover delay lets ToolTips teach without visually interrupting users who already know the icon.
- **Docking toolbar or palette**: a control strip that reconfigures between a compact edge-attached bar and a small floating window depending on whether the user drags it away from an edge.
- **Contextual (pop-up or mini) toolbar**: a small set of icon buttons that appears next to the cursor, scoped to the currently selected object's type (text formatting for text, shape properties for a drawing object).
- **Ribbon control**: an oversized tabbed toolbar with textual group labels, combining menu-like organization and toolbar-like direct access, customizable in the same spirit as classic toolbars.
- **Tool palette vs. toolbar**: mutually-exclusive mode-switching controls (only one operating mode active) vs. immediate-access commands that act on the current selection.
- **Sidebar / task pane / drawer**: modeless panels that replace dialog-driven property editing. A drawer trades some of that modeless convenience back for screen space by stowing offscreen until summoned.
- **"Support both mouse and keyboard use for navigation and selection tasks."** Design every mouse idiom with a keyboard equivalent where feasible, since a meaningful share of users struggle with fine pointer control.
- **"Use cursor hinting to show the meanings of modifier keys."** When a modifier key changes what an action will do, change the cursor to communicate the new behavior in real time.
- **Object-verb ordering vs. verb-object ordering**: the two possible command grammars. GUIs favor object-verb (select, then act) to avoid open-ended, stateful command parsing, at the cost of introducing "selection" as its own concept.
- **"Single-clicking selects data or an object or changes the control state."**
- **"Double-clicking means single-clicking plus action."** Every double-click meaning must subsume its single-click meaning, and any double-click function needs an accessible single-click equivalent for users who find double-clicking difficult or impossible.
- **Chord-click**: pressing two mouse buttons together (or adding a second button mid-drag), most usefully as a "cancel this drag" gesture.
- **"Mouse-down over an object or data should select the object or data."**
- **"Mouse-down over controls means proposing an action, mouse-up means committing to an action."** This is **pliant response hinting**: the control visually previews the pending state change on mouse-down and only commits on mouse-up, giving the user a graceful way to abort by dragging off the control.
- **Debounce (drag threshold)**: ignore small mouse movements (roughly 2-3 pixels) after mouse-down so an intended click or select isn't misread as an accidental drag, only beyond the threshold does the interaction commit to a drag. **"Debounce all drags."**
- **Asymmetric (axially biased) drag threshold**: a non-square, "spool-shaped" threshold zone that favors the far more common drag direction (for example horizontal reordering) while still requiring a larger, deliberate movement to commit to a rarer alternate interaction (for example vertical interspersing) mapped to the same gesture space.
- **"The selection state should be visually evident and unambiguous."** Never rely on color alone.
- **Marching ants / marquee**: an animated dashed or flashing outline used to mark a selection so it remains visible regardless of the underlying image's colors.
- **"Drop candidates must visually indicate their receptivity."** The object under the cursor during a drag, not the cursor itself, should show whether it will accept the drop.
- **"The drag cursor must visually identify the source object."** Don't overload the cursor with drop-target feedback. Cooper calls out Microsoft's "not-permitted" circle-and-bar cursor hint as conflating two separate, and separately weak, idioms, and as needlessly negative framing.
- **Insertion target**: a visual marker (a bar or caret) shown between existing items to indicate where a dragged object will be inserted, distinct from a "land on top of an object" drop target.
- **"Any scrollable drag-and-drop target must auto-scroll."** Trigger auto-scroll just inside the scrollable region's edge (not outside the window, which fails when the window is maximized or full-screen), with a short delay before it engages and a speed that increases the closer the cursor gets to the edge, so users retain control.
- **"Any program application that demands precise alignment must offer a vernier."** A modifier-key-driven fine-motion mode (for example a 10:1 mouse-to-object movement ratio) or arrow-key nudging for pixel-precise placement. Desensitize the mouse once vernier mode engages so releasing the button doesn't jitter the final position.
- **Modal tool / tool palette mode**: selecting a tool locks the canvas into that tool's single behavior until the user explicitly switches tools. Works well with a small tool count, becomes disruptive excise as the working set of tools grows past roughly a handful.
- **Charged cursor**: selecting a tool or object type loads a single instance onto the cursor. The next click (or click-and-drag for custom sizing) deposits exactly one instance and then reverts, useful for graphic object creation (PowerPoint shapes) more than for functions.
- **Constrained drag**: a modifier key (typically Shift) locks a drag to a single axis or locks a resize to the original aspect ratio, determined by the drag's initial predominant direction.
- **Resize handles / vertex handles / Bézier handles**: successively more granular control points for reshaping an object, from whole-bounding-box corners and edges, to individual polyline vertices, to full curve-control points for Bézier shapes.
- **Rubber-banding**: the animated connector line that stretches live between a fixed anchor object and the current cursor position while the user drags out a connection (as in PERT or org-chart diagrams), snapping to a permanent link on release over a valid target.
- **Picking problem** (3D): when objects overlap or are transparent or wireframe, it's hard for the user, and the system, to disambiguate which one the cursor is over. Mitigations include name or attribute-based selection, hover menus listing overlapping candidates, and fluid navigation (zoom or orbit) that reduces the need for precise picking in the first place.
- **Baseline grids, depthcueing, shadows, and poles** (3D): idioms that restore spatial orientation lost when projecting a 3D scene onto a 2D screen without parallax, by dimming distant surfaces, projecting object outlines onto reference grids, or anchoring an object to a grid with a vertical reference line.

## How to apply

- Before adding any dialog, secondary window, or settings screen, ask what user goal it serves and whether an existing pane can serve it instead. Default to integrating tightly-coupled controls into the main content view.
- Default sovereign, content-centric apps to a maximized or full-screen posture. Reserve windowed or pluralized states for transient utility apps or explicit cross-app drag-and-drop workflows.
- For any sovereign app beyond trivial complexity, design a multipane layout (navigation or index pane feeding a content pane) rather than relying on modal navigation between separate screens.
- Write menu item labels as short verbose phrases that explain the action ("Open Report," not "Open"), keep the full function set represented somewhere in the menus, and add matching icons plus keyboard-accelerator hints next to each item.
- Gray out (don't hide) inapplicable menu items and inapplicable toolbar controls, so layouts stay spatially stable and the disabled state itself teaches context.
- Give every frequently-used function a toolbar presence in addition to its menu entry, and add a ToolTip to every icon-only control.
- Reserve tool palettes for genuinely mutually-exclusive modes, and if the tool count grows past a handful, invest in keyboard shortcuts or modifier-key variants so experienced users can avoid palette round-trips.
- Prefer sidebars or task panes over modal or modeless dialogs for object-property editing in authoring tools. Add a global show/hide keystroke so power users can reclaim screen space.
- Implement selection with mouse-down (not mouse-up) commit, add a debounce or drag threshold (a few pixels) before treating movement as a drag, and make the selected state visually bold and non-color-dependent.
- For any drag-and-drop interaction: show source identity on the cursor, show receptivity on drop candidates (not on the cursor), auto-scroll near scrollable edges with a ramping speed and short activation delay, and give an explicit cancel path (Esc, chord-click, or drag back off all candidates).
- Support keyboard equivalents for essential mouse-driven navigation and selection so users with limited pointer dexterity, or touch typists, aren't forced into the mouse.
- Design accelerators by triaging functions into "always," "never," and "sometimes" daily-use buckets, and always display the assigned key next to its menu item.

## Watch out for

- Piling functions into one-dialog-per-feature just because that mirrors the codebase's internal decomposition. This is the most common source of "unnecessary rooms" bloat in real products.
- Cascading or hierarchical submenus: they demand precise two-axis mouse control and hide the command set menus are supposed to teach. Use sparingly, only for rarely-used functions in advanced sovereign apps.
- Flip-flop menu items whose label swaps between two phrasings of the same toggle: ambiguous about whether it's an action or a status.
- Letting disabled toolbar controls disappear rather than gray out: users memorize toolbars by position, and a shifting layout erodes trust.
- Overloading the drag cursor with "can" or "can't drop here" feedback instead of hinting on the drop candidate itself. Doing so with a negative "not permitted" symbol reads as a warning of harm rather than neutral "nothing will happen."
- Modal tool palettes with a large working set of tools: past roughly a handful, the excise of constantly switching modes overwhelms the benefit, even though modality itself isn't the real culprit (tool count is).
- Non-standard, inconsistent modifier-key overloads (the chapter singles out Illustrator's Alt-key behavior, where the same key means different things depending on click order), which are powerful for daily professional users but nearly unusable for casual ones.
- Double-clicking on controls that have no double-click meaning: the extra click is either silently discarded or misinterpreted as a second independent click, producing unpredictable toggling or side effects. Avoid requiring double-clicks where a single click would do, and never rely on double-clicking as the only way to reach a function given its accessibility cost.
- Contiguous-selection interfaces that allow disconnected, non-adjacent multi-selection: technically possible but usually not worth the risk of invisible, hard-to-track selections spread across scrolled-off content.
- Carrying a relative-pointer or cursor metaphor onto touchscreens: touch is naturally absolute and direct, and layering a mouse-style cursor on top of finger input is confusing rather than helpful.
