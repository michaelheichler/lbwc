# Design Details: Controls and Dialogs

Source: About Face: The Essentials of Interaction Design, 4th Edition (Cooper, Reimann, Cronin, Noessel, 2014), Chapter 21.

## In one line

Every standard GUI control and dialog type has a correct job and a set of misuses, and the worst offenders (error, alert, and confirmation dialogs) should mostly be designed out of existence rather than polished.

## Core ideas

- Interaction has a grammar. Imperative controls are verbs (buttons), selection and entry controls are nouns (check boxes, lists, text fields), and display controls manage how information is shown (scrollbars, splitters). Picking the wrong grammatical category for a control confuses users about what will happen when they touch it.
- Affordance must match behavior. A control's visual shape sets an expectation (buttons look pressable, links look navigable, check boxes look bi-state). When flattened or reused across categories, that expectation breaks and learnability suffers. Flat design only survives because decades of prior training already taught users what a rounded rectangle means.
- Pliancy confirms action. Controls should visibly react when activated (indent, highlight, animate) so the user knows the input registered. Silence after a click reads as "did that do anything?"
- Links are for navigation, buttons are for action. Users have learned this convention from the web. Violating it (a link that fires a destructive action, or a "cheap" button next to a disguised link for the paid option) causes confusion, and in dark-pattern cases, erodes trust.
- Selection versus imperative is a design choice, not a fixed rule. Traditionally selection controls needed an explicit imperative (a button) to commit. It is fine to let a selection double as an imperative only when the effect is immediately visible and cheaply undoable (a font-size dropdown, for example). Otherwise keep them separate so users can compose a choice before committing.
- Bounded input beats validated input beats unbounded input. A control that only allows valid values (slider, spinner, drop-down) is stronger than a free-text field with validation, which is stronger than an unrestricted field. Rejecting an out-of-range value after entry is not the same as bounding, it is just rudeness with an extra step.
- Multiple selection needs its own visual idiom once items can scroll off screen. Standard list selection is mutually exclusive at a glance only when everything is visible at once. Once scrolling hides prior selections, users lose track of what is chosen. Reuse the check box (a control already known to be non-exclusive) instead of inventing new behavior for the old selection idiom.
- Horizontal scrolling destroys text readability because it hides the leading characters of every visible line at once. It is fine for grids or spreadsheets with locked headers, or for images, never for a column of prose or names.
- Text edit fields signal "you can change this." Using them for read-only output tricks users into thinking they can edit the value (disk free space, for example). Reserve edit controls for editable data and use plain display or text controls for output.
- A dialog is "another room." Every trip to a dialog costs the user context and flow. Only send users there for things that are genuinely out of the main flow, dangerous, rare, or worth concentrating in one place (a single object's properties, a whole function's options). Frequent, safe, everyday actions belong in the main window's controls, not behind a modal door.
- Modal versus modeless is a scope contract, not a visual style. Modal freezes the app and operates on a selection that cannot change mid-dialog, so its behavior is simple to reason about. Modeless stays open while the user keeps working, so its scope (what happens if the selection changes underneath it) needs careful design. Mixing their conventions (modal look with modeless behavior, or the reverse) is what confuses users, not the mode itself.
- Dialogs serve five distinct informational purposes (property, function, process, notification, bulletin), and mismatching the purpose to the wrong modal or modeless convention or button set is a common source of interaction bugs.
- Error, alert, and confirmation dialogs (bulletins) exist mostly to protect the application or the developer, not the user. They interrupt, they blame, and they rarely prevent the underlying problem. The chapter's central claim is that almost all of them can and should be engineered away by making bad states impossible or automatically recoverable, not by wordsmithing the dialog text.
- Confirmations fail because of habituation. If a dialog is shown routinely, users learn to dismiss it without reading, so it provides zero protection exactly when a truly dangerous action finally occurs (the boy-who-cried-wolf effect). A confirmation is only doing its job on the rare occasions the user says no, and if users usually say yes, it is not earning its interruption.
- Negative feedback from software reads as humiliation, not correction, because software has no standing to judge the user (no shared context, no earned authority the way a coach or teacher has). Positive or neutral feedback teaches better and preserves goodwill.
- All interaction idioms have practical limits. Tabs, radio button groups, and similar list-like idioms work at small counts and degrade badly past a threshold (roughly five or six). When a control set outgrows the idiom, split it into more dialogs or screens rather than stacking or overloading the same control.

## Named patterns and principles

- **Imperative, selection, entry, and display controls**: the four functional categories of controls, grouped by the user's goal (execute a verb, pick a noun, type a noun, or manage the view). Use this taxonomy to check that a given control's category matches how you intend users to interact with it.
- **Dynamic visual hinting**: a control visually changes state when activated (pressed, checked) to confirm the action took effect. Apply it to every actionable control, its absence is read as a possible failure.
- **State-switching button (idiom to avoid)**: a single button that toggles between two icons representing two future actions (play and pause on one button, for example) without a distinct pressed-state indenting. It is ambiguous whether the icon shown means "current state" or "action if clicked." Avoid it, use two buttons, a labeled toggle, or a switch control instead.
- **Earmarking**: adding a check box next to each row in a list control to represent multi-selection explicitly, instead of overloading the list's normal (mutually-exclusive-looking) highlight selection. Use whenever a list can scroll and supports multiple selection.
- **Bounded vs. unbounded entry controls**: bounded controls (sliders, spinners, drop-downs) only ever produce valid values by construction. Unbounded controls (free text fields) can produce anything, valid or not. Use bounded controls whenever the valid value set is finite or has known limits, and reserve unbounded fields for genuinely open-ended input.
- **Active validation**: the control rejects invalid keystrokes as they are typed (blocking non-numeric characters, for example), and must explain the rejection immediately so it does not feel arbitrary.
- **Passive validation**: the control waits until the user finishes (loses focus, pauses past a countdown, or tries to submit) before judging validity, useful when validity cannot be judged character by character. Pair with a short idle-timer (about half a second) so fast typers are not interrupted mid-thought.
- **Hints**: a ToolTip-like pop-up that explains acceptable input for a validation control, appearing on an invalid keystroke or on hover, so users get help instead of a blunt rejection.
- **Process dialog**: a dialog the app opens unilaterally to show a lengthy operation is progressing normally, not crashed. It should show that time is passing (animation), give a completion estimate, and offer Cancel (and ideally Pause). Reserve it for operations genuinely separate from the main window. If the operation is core to the main window's job (copying files in a file browser, for example), show progress in that window instead of a separate dialog.
- **Five purposes of dialogs**: property (view or edit attributes of a selection, usually modeless, often better as a sidebar), function (configure and run a single action, usually modal, and should let configuration and invocation be triggered separately), process (report on a long-running task), notification (report events from outside the user's direct request, such as messages or alarms, collected in a notification center), bulletin (error, alert, confirmation, launched unrequested by the app to serve the app's own state, and the main source of bad interactions).
- **Tabbed dialogs**: group parallel or successively-deeper option panes under one dialog when the grouped controls have a genuine, well-defined relationship to a shared topic. Do not use as a dumping ground for unrelated settings.
- **Stacked tabs (anti-pattern)**: so many tabs they wrap into multiple rows, forcing hunt-and-click to find the right pane and causing rows to reflow disorientingly when clicked. Split into separate dialogs instead.
- **Expanding dialogs**: a "More" or chevron control that reveals additional, usually advanced, controls on demand, letting the dialog serve both novice and expert users. Remember its expand or collapse state between invocations, and always include a way back to the simple state.
- **Cascading dialogs (idiom to avoid)**: a dialog that launches another dialog on top of itself, sometimes several deep, each with its own terminating buttons, so the scope of "OK" and "Cancel" at each layer becomes ambiguous. If your design needs this, restructure with tabs, sidebars, or toolbars instead.
- **Bulletin dialogs, errors, alerts, confirmations**: the three unrequested, application-initiated dialog types that mostly exist to offload the app's own uncertainty onto the user. The chapter's stance is to design these out wherever possible rather than merely improve their wording.
- **Do, don't ask**: the principle for replacing confirmation dialogs. If your research supports that an action is correct, let the software take it with confidence and back it with Undo, rather than asking permission first.

## How to apply

- Classify every control you design or evaluate as imperative, selection, entry, or display, and check its visual affordance matches that category (buttons look pressable and act instantly, links look navigable and never trigger destructive actions).
- Prefer bounded controls (dropdowns, sliders, spinners, steppers) over free-text entry whenever the valid value set is finite or range-limited. Reserve unbounded text fields for genuinely open-ended content.
- When adding multi-select to a scrollable list, add check boxes per row (earmarking) instead of relying on plain highlight-based selection.
- Never scroll plain text lists horizontally. Shorten labels, wrap text, widen the control, or use tooltips or ellipsis truncation instead.
- Keep read-only values in display (non-editable) controls, and make truly editable values editable in place, matching input and output to the same control wherever feasible.
- Default to putting frequent, safe actions in the main window (toolbars, sidebars, inline controls). Reserve dialogs for rare, dangerous, or single-object or single-function concentrations of controls.
- Pick modal only when the operation must lock the current selection and stop everything until resolved. Give it clear OK and Cancel terminating buttons that never change label. Pick modeless only when users need to keep working while the panel stays open. Give it a Close control in the title bar, not terminating buttons, and back its live edits with a global Undo instead of a "cancel all" concept.
- For any long-running operation, show real-time progress with an animated indicator, a completion estimate, and Cancel (plus Pause if resumable). Embed the indicator into the relevant main-window surface (a tab, a status bar) instead of popping a separate dialog when the operation is core to that surface.
- Treat every error, alert, or confirmation dialog you are about to add as a design failure to interrogate first. Can the bad state be made impossible (bounded controls, autocomplete or lookup instead of free typing)? Can the app self-correct (substitute a sane default, remember prior choices)? Can the action just be made fully undoable so no permission-asking is needed at all?
- If a bulletin dialog truly cannot be eliminated, make it polite (never imply user fault), illuminating (explain the actual problem and its scope), and helpful (offer one-click remedies), not just factually accurate.
- Cap tab counts and similar repeated-idiom control groups at a small number (five or six). Once you need to add more, split into separate dialogs or screens rather than stacking rows or overloading a single idiom.
- Never chain a dialog that launches another dialog. If you need drill-down configuration, use tabs, a sidebar, or a toolbar-launched dialog instead of cascading.

## Watch out for

- Flattening a control's 3D affordance (buttons, check boxes) trades visual cleanliness for reduced learnability, especially for new users. Only rely on it where the shape convention (rounded rectangle, square check box) is already deeply trained into your users.
- Disguising a costly option as a plain hyperlink next to a prominent "default" button is a manipulative dark pattern. It can win short-term conversions but damages trust in the product and brand.
- Toggle-style buttons that swap their icon to show the "next" state rather than the "current" state (play and pause on one button, for example) are ambiguous about what the button currently represents. Most audio apps still ship this broken idiom, do not copy it uncritically.
- Icon buttons are only easy to use once learned. First-time users cannot reliably decode an icon's meaning without a text label or tooltip, so do not rely on icons alone in interfaces meant for infrequent or novice users.
- Dynamically changing a terminating button's label (Cancel becoming Apply or Close depending on state) is disorienting. Keep OK and Cancel semantics fixed.
- A confirmation dialog that fires routinely trains users to dismiss it reflexively, so it provides no actual protection by the time a genuinely dangerous action occurs. If you find yourself confirming "are you sure?" on a fully-undoable action (moving a file to a recycle bin, for example), delete the confirmation, not the recycle bin.
- Reflexively adding validated text fields for things like zip codes, dates, or measurements is weaker than making the field understand and normalize the input itself (recognizing "5in" or "5mm," or offering a combo box with named presets like "Best Fit").
- Do not treat an out-of-band environment change (printer disconnected, network unreachable, hardware unplugged) as automatically an "error" requiring an interruptive dialog. Treat it as a normal, expected state of modern connected devices and handle it gracefully (queue, retry, sync later) wherever the stakes allow.
- Treat true system-wide, all-applications-halt dialogs as reserved for genuine catastrophes only (imminent hardware failure, for example). Application-modal is almost always the right, narrower scope.
