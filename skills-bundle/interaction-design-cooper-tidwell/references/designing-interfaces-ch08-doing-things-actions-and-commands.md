# Doing Things: Actions and Commands

Source: Designing Interfaces: Patterns for Effective Interaction Design, 3rd Edition (Tidwell, Brewer, Valencia, 2020), Chapter 8.

## In one line

Actions are the verbs of an interface, so choose the right mechanism to expose them (buttons, menus, gestures, hover, panels), make them visible or learnable through affordance, and for complex tools give users the safety net of preview, undo, history, and macros.

## Core ideas

- The chapter frames all interface work as nouns (objects, layout, structure) versus verbs (the actions people take on those objects: start, cancel, configure, manipulate, transform, delete, create). This chapter is entirely about verbs.
- Most action patterns originated in hardware or physical-world behavior (cut/copy/paste as a clipboard metaphor, drag-and-drop as picking up and putting down objects) and have since hardened into near-universal software conventions. Don't invent new conventions for solved problems, users already know how menus, right-click, drag-and-drop, and clipboard behavior work, so following platform standards buys instant fluency and frees your design energy for the features that actually differentiate the product.
- Mobile and desktop favor different action models. Mobile relies on direct, one-object-at-a-time gestures (tap, swipe, pinch, rotate, shake) applied straight to the object on screen. Desktop relies more on indirect, two-step interaction: select an object, then go elsewhere (a menu, toolbar, button) to apply a command to it. Match your action model to the platform's dominant interaction style rather than porting one platform's conventions onto the other.
- Single-click versus double-click carries a learned meaning on object-oriented desktop OSes: single-click selects (marks a target for a subsequent command), double-click opens, launches, or edits in place. Respect this distinction rather than repurposing it.
- Keyboard actions (shortcuts and tab order) exist for two overlapping reasons: speed for expert users who want to keep hands on the keyboard, and access for users who rely on assistive technology and cannot use a mouse. Treat keyboard support as an accessibility requirement, not just a power-user nicety.
- "Invisible" actions (keyboard shortcuts, double-click behaviors, typed commands) are powerful but undiscoverable by nature, users can't read them off the screen the way they read a menu or button label. Always pair invisible actions with a discoverable equivalent (a visible menu item, a labeled button) so new users can learn what's possible, reserve invisible-only actions for well-established conventions.
- Affordance is the visual promise that an object can be acted on (a raised button affords clicking, a scrollbar affords dragging, blue underlined text affords tapping). Treat every visually distinctive element on the screen as an implicit promise, if something looks special or manipulable, it should actually do something, and if something does something, it should look distinctive enough to invite the action.
- Time-based response guidelines (attributed to Norman/Nielsen research) set expectations for latency: under about 0.1s feels instantaneous and needs no feedback, from about 0.1 to 1s the user notices the delay but stays on task, past about 1s the user starts doubting the system is working and may abandon the task, and at that point a spinner or loading indicator becomes mandatory. Users tolerate longer waits far better when the system visibly shows it's "thinking," so almost always favor showing some progress signal over silence, even if the wait doesn't actually shrink.
- Reversibility (preview, undo, cancel) exists to support "safe exploration," the psychological freedom to try things because mistakes are cheap. This safety net benefits both novices (fear reduction) and experts (fast, low-cost iteration on creative variations), and is a repeated theme tying together Preview, Cancelability, and Multilevel Undo.
- Building true multi-step Undo, Command History, or Macros requires the underlying software to model user actions as discrete, named, and often reversible operations. This is straightforward to design in from scratch but hard to retrofit into an existing architecture that wasn't built around an action model, factor this into technical risk assessment before promising these features late in a project.
- Not everything should be undoable. Transient or view state (selection, scroll position, window position, cursor location, in-progress modal edits) is generally excluded from undo history. Committed, potentially destructive changes (text edits, database transactions, image edits, layout changes, file operations, cut/copy/paste) generally should be included. Some operations (a completed purchase, a sent email, a posted forum message) are inherently irreversible in the real world, and users generally understand this from context, so don't force fake reversibility onto them.

## Named patterns and principles

- **Button Groups**: cluster related action buttons together with shared visual treatment (same size, spacing, alignment) when you have several actions of the same scope to keep visible. Use when actions have similar or complementary effects and there are roughly two to five of them, and never mix actions of different scope in one group. Works because Gestalt proximity and similarity cues let users infer relatedness at a glance, turning a pile of buttons into a self-describing visual hierarchy. Give any single primary action within a group a stronger visual treatment. Place groups beside (not below) the objects they act on, to avoid the "blind spot" at the bottom of lists and tables.
- **Hover or Pop-Up Tools**: hide per-item action buttons until the user hovers the pointer over the item (or taps it, on touch), then reveal them right where they're needed. Use in list-style UIs (messages, search results, photos) with many items that each need several actions, when you want a clean baseline look but a mouse-driven audience. Works because it reveals controls exactly on demand without permanently consuming space, and the rollover gesture is simpler and more discoverable than opening a menu. Respond instantly on hover and unhover with no animated transition, and never resize or reflow the layout when tools appear. Has no real touch equivalent, since there's no hover state, use a tap-triggered overlay instead on touch devices.
- **Action Panel**: a persistently visible, freely structured panel of commands (not a flat menu) placed near the object it acts on, showing the most relevant or common actions for the current context. Use when you have too many or too complex a set of actions for a menu bar or pop-up menu, especially when actions need grouping that doesn't map to standard menu categories, or when you want maximum discoverability without a traditional document or menu-bar model. Works by trading hidden menu structure for full visibility and unconstrained layout (lists, grids, categorized groups, trees), unlike a menu's forced single-column list. Make the panel's contents dynamic (they should change with app or selection state), and prefer longer, fuller text labels than a menu would use since first-time users benefit from more explanation.
- **Prominent "Done" Button or Assumed Next Step**: give the final, committing action of a flow (Submit, Done, Buy, Continue) unmistakably strong visual weight and place it at the natural endpoint of the user's visual and task flow (usually bottom or bottom-right). Use for the last step of any transaction or settings commit. Works because a visually obvious, singular conclusion gives users closure and confidence the action actually took effect, reducing hesitation and task abandonment. Prefer specific verb labels ("Buy," "Send") over generic ones ("Done") where a specific label communicates the outcome better. Avoid splitting attention across two visually equal calls to action on the same screen.
- **Smart Menu Items**: menu, button, or link labels that dynamically insert the specific object or operation they'll act on ("Undo Increase Clarity," "Add Jane Doe to Contacts" instead of "Undo" or "Add sender to Contacts"). Use whenever an action's effect depends on current selection, state, or history (Close, Undo, contextual per-item commands). Works because it removes the guesswork about what will be affected, preventing accidental action on the wrong object and encouraging safer exploration since users can trust the label to be literally true. Disable the item entirely when there's no valid target, and consider a plural label ("Delete Selected Objects") for multi-select cases.
- **Preview**: render a lightweight, realistic sample of an action's outcome before the user commits to it (filter thumbnails, product configurators, print layout preview). Use before any "heavyweight," slow, hard-to-reverse, or visually unpredictable action (large file operations, purchases, image filters, form submission with a lot invested). Works because it prevents costly mistakes by letting users catch errors before committing, and it teaches what an action does better than documentation, exactly when and where the user needs to know. Let the user commit directly from the preview, and always give a clear way to back out or correct inputs rather than forcing a restart.
- **Spinners and Loading Indicators**: an animated signal shown after the user acts and before a response arrives. A spinner is stateless ("something is happening"), a loading indicator shows measurable progress (percent complete, bytes processed, time remaining). Use spinners for short unpredictable waits, loading indicators for longer waits where progress can be measured. Follow the response-time bands, no indicator needed under about 0.1s, optional for sub-second delays, mandatory past about 1s. Works because visible progress substantially increases user patience even when the actual wait time is unchanged, since it confirms the system hasn't hung. Time estimates can start rough as long as they converge to accuracy over time. Keep the rest of the UI responsive rather than freezing it while the indicator runs, and pair it with a cancel affordance when the operation is cancelable.
- **Cancelability**: give the user a way to instantly stop a time-consuming or blocking operation with no side effects, via a clearly labeled Cancel or Stop button (or standard stop icon) placed next to the loading indicator or wherever results will appear. Use for any operation that runs uninterrupted for more than about two seconds, or that shuts out other interaction (a modal dialog, a long query, a print job). Works because it satisfies the "user control and freedom" usability heuristic, users change their minds or trigger actions by accident, and knowing they can bail out encourages the same safe exploration Preview and Undo support. Cancel must take effect within a second or two or users will distrust it. When multiple operations run in parallel, make each one's cancel target unambiguous (label it with the specific thing being canceled, as in Smart Menu Items).
- **Multilevel Undo**: the ability to reverse a sequence of recent actions one at a time, most recent first, typically alongside Redo to move forward again. Use in any complex, highly interactive application (editors, authoring tools, graphics software, programming environments) where users perform long sequences of actions and need to safely explore or recover from mistakes. Works because it removes the fear of permanent damage from experimentation for novices and experts alike, and lets expert users try, evaluate, and discard whole work paths quickly, preserving creative flow. Requires the software to model actions as discrete, named, reversible units. Keep an undo stack at least 10 to 12 items deep, define undo granularity in terms the user thinks in (undo a typed phrase, not a single keystroke), exclude transient or view state from the stack, and always surface the specific pending undo or redo action via Smart Menu Items so users aren't reasoning about an invisible stack abstraction.
- **Command History**: a persistent, visible, user-manipulable record of the sequence of actions taken (distinct from Undo, which is about reversing, History is about reviewing, searching, and sometimes reordering or replaying). A related variant is browser-style history, a searchable log of visited locations. Use for long or complex sessions where a user may need to repeat a forgotten action, recall ordering, replay a sequence on a different object, keep an audit log, or seed a macro. Works because it externalizes memory of what was done, supporting review, compliance, and reuse without relying on the user's recall. Record actions at a granularity matching user intent (one bulk operation on 17 objects is one history entry, not 17). If an action is undoable it should also appear in history. Display history as an optional, secondary panel, oldest to newest, timestamped if useful.
- **Macros**: a single named, saved action composed of a recorded or assembled sequence of smaller actions, played back on demand, optionally parameterized to act on different objects. Use when users repeat long sequences over many files, records, or objects (batch image processing, spreadsheet automation, cross-app "recipes" like IFTTT). Works because it directly serves the "streamlined repetition" behavior pattern, saving time and cutting the error rate that comes from repeatedly performing the same manual steps, while sustaining flow by compressing many actions into one. Let users name, review, and edit macros, allow macros to call other macros, make them searchable and sortable, and let them run parameterized or in bulk (batch mode). If your users don't see themselves as programmers, don't call the feature "programming," frame it as recording and reuse to avoid scaring them off. If macros can trigger meaningful side effects, design in constraints against abuse.

## How to apply

- Default to platform-standard conventions for common actions (clipboard, drag-and-drop, context menus, keyboard shortcuts) rather than reinventing them, and spend your design effort on what's actually novel about the product.
- Choose the action-exposure mechanism to match density and discoverability needs: Button Groups for a small fixed set of always-visible related actions, Hover Tools for many per-item actions that would otherwise clutter a list, Action Panel for a large or awkwardly categorized action set that needs full visibility and freeform layout.
- Give every screen or flow one visually dominant "Done"-style action at the natural end of the task flow, and make sure any invisible-only action (shortcut, double-click, gesture) also has a discoverable, visible equivalent.
- Make every visually distinctive UI element correspond to a real available action (affordance should never be decorative-only) and make every important action visually distinctive enough to be found.
- Use Smart Menu Items wherever a command's effect depends on context, so labels state the literal effect rather than a generic verb.
- Before a costly, slow, or hard-to-predict action, show a Preview if at all feasible.
- For any operation likely to run past about a second, show a spinner or loading indicator and provide Cancelability. Keep the estimate-quality bar low (rough is fine, converging is what matters) but keep the rest of the UI alive.
- For any complex, high-frequency-use tool, evaluate up front whether it needs Multilevel Undo, Command History, and Macros, since these require an action-model architecture that is costly to retrofit later. Decide before, not after, building the object or command model.
- When designing undo or history granularity and scope, always define it around how the user thinks about their work, not around internal data structures or algorithms.

## Watch out for

- Cryptic icon-only toolbars are a classic usability failure, don't rely on icons alone when the action can't be unambiguously drawn, fall back to text labels or combo boxes.
- Drop-down menus and combo boxes are for selecting form values, not for performing actions, don't overload them as an action-triggering mechanism.
- Invisible actions (keyboard-only, double-click-only) can't be discovered by inspection, so an interface relying solely on them locks out both new users and users who can't use a mouse.
- On touch devices, Hover Tools have no equivalent since there's no hover state, don't assume the pattern ports directly, use tap-revealed overlays instead.
- A "global metaphor" of literal physical friction (multiple redundant confirmation clicks, forced navigation to a separate menu just to act on a selection) doesn't belong in mobile direct-manipulation contexts, prefer acting on the object directly.
- Splitting visual prominence across two equally strong calls to action on one screen dilutes the "assumed next step" and confuses which one to take.
- Not all delays deserve a full progress-metered Loading Indicator. A stateless spinner is appropriate when the system genuinely cannot compute how far along it is, don't fake a percentage.
- Don't make everything undoable by default: transient view state (selection, scroll position, panel geometry, in-progress uncommitted dialog edits) usually should not go on the undo stack, and inherently irreversible real-world actions (a completed purchase, a sent message) shouldn't be given false undo affordances.
- Scriptable or macro features can be abused if the application is powerful enough (Excel macros were called out as a case needing deliberate constraints), consider what a malicious or careless macro could do before shipping unconstrained automation.
