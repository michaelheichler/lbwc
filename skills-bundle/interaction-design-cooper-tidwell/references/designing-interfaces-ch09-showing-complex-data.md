# Showing Complex Data

Source: Designing Interfaces, 3rd Edition (Jenifer Tidwell, Charles Brewer, Aynne Valencia, 2020), Chapter 9, "Showing Complex Data."

## In one line

Interactive information graphics (tables, maps, plots, trees, graphs) should let users explore, compare, and drill into data rather than just look at a static picture, and a handful of named interaction patterns (Datatips, Data Spotlight, Dynamic Queries, Data Brushing, Multi-Y Graph, Small Multiples) cover most of what that exploration needs.

## Core ideas

- Information graphics include anything that shows data visually: tables and tree views count, not just charts and maps, because they are built to be read visually even though they are mostly text.
- Interactivity beats static design. Letting the user hide, show, rearrange, and manipulate data turns them into a participant in discovery, not a passive viewer. The act of manipulating the data itself often surfaces things a static version never would.
- Before picking a display, ask what the user is trying to learn. A user hunting one specific fact (a street, an address) needs strong search and filtering to zero in. A user trying to build a mental model of a whole system (a city layout, a biological process) needs overviews plus the ability to zoom in and back out. Design for whichever goal dominates.
- Good interactive data graphics should let a user answer six questions: how is this organized, what relates to what, how do I explore it, can I rearrange it, how do I narrow it to what I need, and what are the exact values. Use this as a checklist against any data view you design.
- Pick an organizational model that matches the data's inherent shape: Linear (list, single-variable plot), Tabular (spreadsheet, sortable table, multivariable plot), Hierarchical (tree, tree table), Network of interconnections (directed graph, flowchart), Geographic or spatial (map, scatter plot), Textual (word cloud), or Other (treemap, parallel coordinates). If data fits two models (both geographic and tabular, say), consider showing it both ways. Forcing it into only one model can hide real structure.
- Preattentive variables are visual properties the eye processes before conscious attention, in roughly constant time regardless of how much data is on screen: color, size, alignment, orientation, shape, and others. Plain text values, by contrast, take linear time to scan because the viewer has to read and think about each one. Use preattentive variables (not text alone) whenever you want something to visually pop or want the user to compare classes of data at a glance. This is called encoding, and you can layer several preattentive variables (position, hue, shape) to represent multiple data dimensions in one static display, using redundant encoding (both color and shape, for example) to make groupings unmistakable.
- Layering: a well-designed graphic reads as several transparent layers stacked on the base graphic, each pulled out by a preattentive cue like color. This segments a complex graphic into simpler pieces the viewer can study one at a time while still seeing how they relate.
- Navigation and browsing should follow "focus plus context", let the user zoom into a point of interest while still seeing enough surrounding data to know where they are. Core mechanisms: scroll and pan (drag or scroll for off-screen content, use click-to-load or panning instead of scrollbars when the data set is huge or has unpredictable size), zoom (change scale, not location, to reveal detail without cluttering the overview), open and close points of interest (in-place expand/collapse, as in tree views), and drill down (clicking reveals a deeper view, in a new panel or window). Link search results into these same mechanisms (a searched map location should pan and zoom to it, for example) so users get context and spatial memory for free.
- Sorting and rearranging can reveal relationships that a fixed order (alphabetical, say) hides. Reordering data numerically, by category, by date, or otherwise puts related or extreme values next to each other, which is far easier to compare than scattered values. Give users control over sort order (sortable table columns, draggable columns, reorderable tree children, repositionable diagram nodes) rather than locking in one arrangement. Even something as narrow as changing which series sits at the baseline of a stacked bar chart can make previously invisible variation visible.
- Searching and filtering serve the same user intent (narrow the data to what matters) even though "filtering" and "querying" are technically different operations. The best filter and search interfaces share four traits: highly interactive (respond fast, but don't degrade typing by reacting to every keystroke if that's too slow), iterative (let users refine and chain search then filter), contextual (show results embedded among the surrounding data, not isolated), and capable of complex, multi-condition queries (not just simple on/off toggles) so users can test real hypotheses.
- Getting exact values out of a graphic is a separate concern from seeing overall shape. Match the technique to how precise the user needs to be: labels (precise, placed right at the data point, but clutter the view if overused), legends (needed whenever color, shape, or size encodes a category, keep them on-screen near the data), axes, rulers, scales, and timelines (lower burden on the designer, higher burden on the user, who must interpolate, use these when exact values matter less), and the two dedicated hover patterns, Datatips and Data Spotlight, described below.

## Named patterns and principles

**Datatips**
What: a tooltip-like popup that shows the data value(s) for a point when the user hovers, taps, or clicks it.
Use when: you're showing an overview graphic (map, chart, table) with more detail "hidden behind" each point than you want to render permanently, and the user can point at things with a mouse or finger.
Why: looking up specific values is a common task. Datatips let you keep the overview clean while still answering "what exactly is this" on demand, right where the user's attention already is. It's fast, lightweight, and rewards curiosity.
How: make it appear at the pointer, layered over the graphic, and temporary. Keep the content dense but small so it doesn't obscure the graphic. Position it programmatically to cover as little as possible. Vary the format by context (toggle place names vs. coordinates on a map, for example). Add drill-down links inside the Datatip itself when there's more depth available. An alternative is a reserved static panel next to the graphic that updates on hover, useful when you don't want anything covering the graphic and want the info to persist. Datatips are commonly combined with Data Spotlight.

**Data Spotlight**
What: hovering over one slice of data (a line, a layer, a related group) highlights that slice and dims everything else.
Use when: the graphic is dense enough that its own structure gets lost, or the data has structurally complex "slices" (multiple lines, areas, or point clusters) rather than single simple points. If what's under the pointer is just a single point, use Datatips instead. The two are often used together.
Why: it delivers "focus plus context" by visually quieting the clutter around the point of interest without removing the rest of the data, so relationships stay visible while attention narrows. Fast, flicker-free transitions between spotlighted slices let users perceive both large and tiny differences as they move the pointer, and it makes exploring the data feel engaging.
How: design the graphic to be legible even without the spotlight (someone may print it or view it non-interactively). Spotlighted data should shift to a light or saturated color while everything else fades toward gray, and the reaction should feel instantaneous. You can also trigger a spotlight from legend hot spots, not just the graphic. Consider a "spotlight mode" that only activates after a longer initial hover, to prevent accidental triggering, or use click or tap instead of hover on touch devices (reserving click for drill-down if needed). Pair with Datatips for point-level detail.

**Dynamic Queries**
What: standard controls (sliders, checkboxes, radio buttons, dropdowns, text fields) that let users filter which slices of a data set are visible, with the display updating immediately as controls change.
Use when: you have a large, multivariate data set with a fixed, predictable set of attributes (numeric, categorical, date, or selectable region) that users need to narrow down, whether to eliminate noise, test criteria, understand relationships, or just explore. Also applies to faceted search over rich item collections.
Why: it's easy to learn (no query language, just familiar controls expressing simple Boolean logic like "price between X and Y"), it turns exploration into an interactive back-and-forth that keeps users in flow because feedback is immediate, and the controls themselves teach the user what's queryable (a 0-100 slider tells you the attribute's range just by existing).
How: match control to data type: sliders for a single number in a range, double sliders or slider pairs for a bounded subset of a range, radio buttons or dropdowns (often with an "All" option) to pick one value or data set, checkboxes or toggles for an arbitrary subset, text fields for precise values (at the cost of typo risk). An alternative is direct on-graphic selection (draw a box to keep or remove a region), which is direct but only works when data can be spatially selected. See Data Brushing for the tradeoffs of that approach.

**Data Brushing**
What: selecting data in one view highlights that same data simultaneously in one or more other linked views of the same data set.
Use when: you can show two or more graphics of the same underlying data at once (a scatter plot and a table, a map and a timeline, a diagram and a tree, for example).
Why: it lets the user select points visually, which is often easier than defining a selection numerically (an outlier is easy to circle, hard to describe as an equation), and then see those selected points in a completely different context, which can surface insight that a single view can't. This is an instance of the larger principle of coordinated or linked views, where interactions like zoom, pan, and selection in one view are mirrored across all views, reinforcing that they are just different lenses on one data set.
How: decide the selection gesture (tap, click, range toggle, single vs. multiple, contiguous vs. scattered) the same way you'd design selection for any collection. Make the other views update immediately, since lag kills the effect. Keep the visual treatment of brushed points consistent across every view (color hue is the most common choice) so they read as one perceptual layer no matter which view the user looks at.

**Multi-Y Graph**
What: stack multiple graph lines or panels so they share a single x-axis, even when each has its own y-axis, scale, or units.
Use when: you have two or more graphs (line, bar, area, or a mix) that share the same x-axis, typically time, but otherwise represent different variables, and you want viewers to spot vertical relationships (correlation, timing, divergence) between them.
Why: aligning on a shared axis tells the viewer these data sets are related and enables direct side-by-side, position-matched comparison that separate unaligned charts would not support.
How: stack the panels vertically, one shared x-axis, separate y-axis space per panel (slight overlap is fine if it doesn't create visual interference). Skip y-axes entirely if exact values don't matter or are already labeled on the chart, in that case just offset the curves so they don't collide. Label each graph clearly, and add vertical gridlines so a viewer can trace one x-value across all the stacked graphs.

**Small Multiples**
What: a set of small, similar pictures (each showing two or three data dimensions) tiled across the screen, with the tiling itself encoding one or two additional dimensions, either as a single strip or a 2D grid.
Use when: your data set has more dimensions than a single picture can show, and side-by-side comparison across that extra dimension matters more than seeing full detail in any one image. Needs real screen space, generally not a fit for small mobile screens unless each tile is tiny. (Sparklines are the exception: tiny, label-free Small Multiples that work fine inline in text or table cells.)
Why: it packs a lot of information into a comprehensible form because each tile tells a small story on its own, and the collection tells a bigger story about how the tiles vary. As Edward Tufte put it, small multiple designs "answer directly by visually enforcing comparisons of changes, of the differences among objects, of the scope of alternatives." Side-by-side tiles beat sequential playback or 3D placement of the same data because the viewer can glance freely without holding earlier frames in memory or mentally rotating a 3D plot.
How: decide whether you're encoding one extra dimension (lay tiles out in a line or wrapped strip) or two (use a 2D grid, one dimension per axis). Label clearly so the varying dimension(s) are unambiguous. Keep every tile visually consistent (same size, same axis scale, same content type) so the differences that remain are the meaningful ones. If a dimension has too many values to tile directly (100, say), bin them into a manageable number of groups, or use shingling (overlapping bins, so some data points appear in more than one tile) to help reveal patterns, and label it clearly so users understand the overlap. Two-dimension small-multiple grids are also called trellis plots or trellis graphs (a term used by William Cleveland and by the S-PLUS and R software packages).

## How to apply

- Start every complex-data screen by asking which organizational model (linear, tabular, hierarchical, network, geographic, textual) actually fits the data, and check whether a second model would reveal something the first hides.
- Decide up front whether the user's goal is "find this one thing" (optimize for search, filter, and drill-down) or "understand the whole shape" (optimize for overview plus zoom and pan and focus-plus-context).
- Use color, size, alignment, or shape (preattentive variables) rather than raw text whenever you need something to be found or compared instantly. Reserve plain text and tables for values that genuinely need to be read one at a time.
- Give users control over sort order and arrangement by default on any table, list, or multi-series chart. Don't hard-code a single sort order and call it done.
- Reach for Datatips whenever an overview graphic hides per-point detail behind a hover or tap target. Reach for Data Spotlight when the "hidden" thing is a whole slice (line, layer, group) rather than a single point, and pair the two when both apply.
- Reach for Dynamic Queries whenever the data set has a fixed set of filterable attributes, wire controls (sliders, checkboxes, dropdowns) to update the display immediately, not on submit.
- Reach for Data Brushing whenever you already show the same data set in two or more views. Let selection in one drive highlighting in all of them, using one consistent visual treatment (usually color) across views.
- Reach for Multi-Y Graph when you need to compare multiple time-aligned (or otherwise x-aligned) series with different units or scales.
- Reach for Small Multiples when a data set has more independent dimensions than one picture can encode and you have the screen real estate for a tiled layout. Use sparklines instead for tight inline spaces.
- Always provide a way to get exact values (labels, legends, axes, or Datatips) even in a highly visual, gesture-driven design. Some users need the precise number, not just the shape.

## Watch out for

- Overusing labels: they are precise and low-friction to read, but too many clutter the graphic and defeat the point of a clean overview. Prefer Datatips or a reserved detail panel for dense data.
- Text tables of numbers with no visual encoding force linear, item-by-item scanning. If some values matter more, encode them with a preattentive variable (color, size) so they can be found at a glance.
- Locking sort order or arrangement to one default (alphabetical, say) can bury interesting relationships in the data that a numeric or category sort would reveal. Give users the reorder control.
- On-graphic drag-select filtering (a Dynamic Queries variant) only works for data that can be spatially selected. If the user can't draw a box around it, they can't query on it, that's a hard constraint on this approach, not just a design nicety.
- Small Multiples need real estate: don't force a large tiled grid onto a small mobile screen unless the tiles are sparkline-scale. And keep the number of tiles manageable, bin or shingle a wide-ranging dimension rather than rendering, say, 100 tiles.
- Data Spotlight should never be the only way to read the graphic. Design the static (non-hovered) state to be legible on its own, since users may print it or view it without interaction.
