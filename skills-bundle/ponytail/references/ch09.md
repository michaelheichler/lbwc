# Chapter 09: Pragmatic Projects

> Scale individual pragmatic habits to the whole team: keep teams small and stable, automate everything, test ruthlessly, and measure success by user delight rather than features delivered.

## Tips in this chapter

- **Tip 84 — "Maintain Small, Stable Teams"** — Teams under ~10-12 people who know and trust each other outperform larger, shifting groups; communication paths explode with size.
- **Tip 85 — "Schedule It to Make It Happen"** — Improvement, experiments, and learning only happen if they are on the backlog; "whenever there's a free moment" means never.
- **Tip 86 — "Organize Fully Functional Teams"** — Build teams so each can deliver a feature end-to-end without handoffs or gates; siloed specialization creates waste.
- **Tip 87 — "Do What Works, Not What's Fashionable"** — Adopt processes by piloting and measuring them, not because a famous company uses them; context always differs.
- **Tip 88 — "Deliver When Users Need It"** — Continuously shorten the delivery cycle toward on-demand; the goal is working software now, not adherence to any methodology.
- **Tip 89 — "Use Version Control to Drive Builds, Tests, and Releases"** — Commits and tags trigger the entire build/test/deploy pipeline; no build should depend on a sacred machine.
- **Tip 90 — "Test Early, Test Often, Test Automatically"** — Small bugs become sharks fast; run the full test suite on every change before they escape.
- **Tip 91 — "Coding Ain't Done 'Til All the Tests Run"** — Passing tests are the definition of done; confidence in a feature comes from the test suite, not from eyeballing it.
- **Tip 92 — "Use Saboteurs to Test Your Testing"** — Deliberately introduce bugs to verify that tests actually catch them; an untested test is no test.
- **Tip 93 — "Test State Coverage, Not Code Coverage"** — Line coverage is a weak proxy; what matters is whether you cover the distinct states the program can be in.
- **Tip 94 — "Find Bugs Once"** — When a human finds a bug, add an automated test for it immediately so no human ever finds it again.
- **Tip 95 — "Don't Use Manual Procedures"** — People are not repeatable; scripts are. Any manual step in build or deploy is a broken window waiting to happen.
- **Tip 96 — "Delight Users, Don't Just Deliver Code"** — Users care about business outcomes, not features; ask how they will know the project succeeded, then optimize for that.
- **Tip 97 — "Sign Your Work"** — Own what you produce; your name on code should mean it is solid, tested, and documented.

## Ponytail relevance

### Automate the repeatable, think about the rest (SUPPORTS)
The Starter Kit (Tips 89, 95) insists that every recurring project operation — build, test, deploy — must be automatic and scripted. Manual steps introduce inconsistency and are the enemy of the lazy dev: you pay the cost every single time. Automation is the one-time investment that eliminates the recurring cost.

### Test ruthlessly so you can move fast without breaking things (GUARDRAIL)
Tips 90–94 are the "not careless" half of laziness. The book frames testing as self-interest: "We are driven to find our bugs now, so we don't have to endure the shame of others finding our bugs later." Tip 94 is especially sharp — once a human finds a bug, automate detection for it forever. Skipping tests is not laziness; it is deferred rework.

### Do what works, not what's fashionable (SUPPORTS)
Tip 87 and the Coconuts topic are pure YAGNI applied to process: don't adopt Scrum, Kanban, or whatever Netflix is doing because it sounds good. Pilot small, keep what works, discard overhead. "A fake airport made out of coconut shells is no substitute for the real thing."

### Deliver sooner, not bigger (SUPPORTS)
Tip 88 frames continuous delivery as the real goal, not methodology compliance. Shorter cycles mean smaller batches, less WIP, faster feedback — all laziness-aligned because you only build what you can immediately ship and verify.

### Quality is built in, not bolted on (GUARDRAIL)
The team-level "No Broken Windows" and "Quality is built in, not bolted on" (Topic 49) push back against deferring quality work to a dedicated QA phase or officer. For ponytail, this means the minimal solution still must meet its own standard; a one-liner that silently corrupts data is not lazy, it is careless.

### Organize to minimize handoffs (SUPPORTS)
Tip 86 advocates fully functional teams that can move a feature end-to-end. Handoffs, gates, and approvals are waste in the Lean sense — invisible overhead that scales with team dysfunction. The lazy org structure is one where the smallest possible group can ship the full thing.

### Sign your work (TENSION)
Tip 97 asks developers to take pride and ownership, which is a mild tension with pure laziness: it demands care and craftsmanship beyond the minimum. The resolution is that "lazy means efficient, not careless" — sloppiness enabled by anonymity is the opposite of what the tip is guarding against.

## Sharpest lines

- "Quality is built in, not bolted on."
- "We are driven to find our bugs now, so we don't have to endure the shame of others finding our bugs later."
- "Once a human tester finds a bug, it should be the last time a human tester finds that bug."
- "Do What Works, Not What's Fashionable" — and the follow-up: "Try it."
