# Chapter 05: Bend, or Break

> Write code that stays flexible and reversible by minimizing coupling, preferring transformations over state, avoiding inheritance, and externalizing configuration.

## Tips in this chapter

- **Tip 44 -- "Decoupled Code Is Easier to Change"** -- Coupling forces parallel changes; reduce it so any one part can change independently.
- **Tip 45 -- "Tell, Don't Ask"** -- Don't reach into an object to read its state and then update it; tell the object what to do and let it manage itself.
- **Tip 46 -- "Don't Chain Method Calls"** -- Limit yourself to one dot per access; chaining five levels deep means five things that can't change without breaking you.
- **Tip 47 -- "Avoid Global Data"** -- Every global (including singletons and mutable external resources) acts as a hidden parameter to every function; it couples everything to everything.
- **Tip 48 -- "If It's Important Enough to Be Global, Wrap It in an API"** -- Mandatory globals deserve a thin interface so the representation can change without touching callers.
- **Tip 49 -- "Programming Is About Code, But Programs Are About Data"** -- Think in terms of the transformation from input to output, not the classes and modules that happen to carry it.
- **Tip 50 -- "Don't Hoard State; Pass It Around"** -- In a transformation pipeline, data flows freely between functions rather than being locked inside objects.
- **Tip 51 -- "Don't Pay Inheritance Tax"** -- Inheritance couples child to parent to grandparent and all callers; the tax compounds every time the hierarchy deepens.
- **Tip 52 -- "Prefer Interfaces to Express Polymorphism"** -- Interfaces and protocols give you polymorphism without any inheritance coupling.
- **Tip 53 -- "Delegate to Services: Has-A Trumps Is-A"** -- Wrap a collaborating object as a field rather than subclassing it; you control exactly which API is exposed.
- **Tip 54 -- "Use Mixins to Share Functionality"** -- Compose named bundles of behavior into classes without entangling their type hierarchies.
- **Tip 55 -- "Parameterize Your App Using External Configuration"** -- Values that might change after deployment (credentials, ports, feature flags, tax rates) belong outside the code, not baked in.

## Ponytail relevance

### Coupling is the enemy of change -- and of minimalism (SUPPORTS)
The book's central claim in this chapter is that "coupling is the enemy of change, because it links together things that must change in parallel." Every hidden dependency inflates the cost of every future edit. The ponytail instinct -- write less, delete over add -- is only sustainable when each piece can be changed in isolation. Tight coupling silently doubles the effort of every subsequent simplification.

### Transformation pipelines: the laziest correct structure (SUPPORTS)
Topics 29--30 show that restructuring code as a series of data transformations -- `input -> f -> g -> h -> output` -- collapses the design into the smallest possible surface. "We need to get back to thinking of programs as being something that transforms inputs into outputs. When we do, many of the details we previously worried about just evaporate. The structure becomes clearer, the error handling more consistent, and the coupling drops way down." This is the multi-step realization of the one-liner instinct: each stage is a small, pure, reusable step.

### Inheritance is hidden complexity debt (SUPPORTS)
Tip 51 names the cost explicitly: every subclass carries the full weight of every ancestor, and callers carry it too. The alternatives (interfaces, delegation, mixins) each do less and couple less. Preferring them is laziness correctly applied -- reach for the smallest tool that expresses the intent.

### Don't chain method calls (GUARDRAIL)
Tip 46 is a concrete, checkable rule: no more than one `.` per access. It is a guardrail, not a license to be cavalier -- the reason to stop chaining is that each extra link is a thing you can't change freely. The exception ("anything in a third-party library should be considered volatile") is itself a reminder to stay alert to external coupling.

### Configuration: move changeable values out of the binary (SUPPORTS)
Tip 55 is pure laziness aligned: hard-coding credentials, ports, or feature flags forces a rebuild and redeploy for every environment tweak. Externalizing them means the code stays smaller and the operational surface stays flexible. The sidebar is the guardrail: don't make *every* field configurable -- 40,000 config variables is its own nightmare.

### Error handling in pipelines (GUARDRAIL)
The book devotes significant space to wrapping values in `{:ok, value} | {:error, reason}` so that errors short-circuit a pipeline without silent data loss. This is the "not careless" half: a transformation chain that silently drops errors on the floor is unfinished code. The minimum correct pipeline always carries error state through.
