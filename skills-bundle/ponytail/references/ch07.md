# Chapter 07: While You Are Coding

> Coding is not mechanical transcription — every minute demands conscious judgment about instincts, coincidences, complexity, correctness, and names.

## Tips in this chapter

- **Tip 61 — "Listen to Your Inner Lizard"** — When coding feels like walking uphill in mud, stop: your nonconscious brain is flagging a real problem with the design or approach.
- **Tip 62 — "Don't Program by Coincidence"** — Rely only on documented, understood behavior; code that works for unknown reasons will fail for unknown reasons.
- **Tip 63 — "Estimate the Order of Your Algorithms"** — Know the Big-O shape of what you write; an O(n²) that works on 1,000 rows may be unusable on 1,000,000.
- **Tip 64 — "Test Your Estimates"** — After reasoning about complexity, actually measure it; the only timing that counts is production speed with real data.
- **Tip 65 — "Refactor Early, Refactor Often"** — Small, continuous refactoring is cheaper than deferred rewrites; treat code like a garden, not a construction project.
- **Tip 66 — "Testing Is Not About Finding Bugs"** — The major benefit of testing happens when you think about and write the tests, not when you run them.
- **Tip 67 — "A Test Is the First User of Your Code"** — Writing a test before code forces you to look at the API from the outside, reducing coupling and clarifying contracts.
- **Tip 68 — "Build End-to-End, Not Top-Down or Bottom Up"** — Build small slices of end-to-end functionality incrementally; neither pure top-down nor bottom-up works because you don't know what you're building when you start.
- **Tip 69 — "Design to Test"** — Build testability in from the start; hard-to-test code is a signal of tight coupling, not a testing inconvenience.
- **Tip 70 — "Test Your Software, or Your Users Will"** — Testing is part of programming; "Test Later" means "Test Never."
- **Tip 71 — "Use Property-Based Tests to Validate Your Assumptions"** — Let the computer generate random inputs against stated invariants; it will find assumption violations your hand-crafted cases miss.
- **Tip 72 — "Keep It Simple and Minimize Attack Surfaces"** — Code complexity directly enlarges the attack surface; simpler, smaller code has fewer opportunities for security holes.
- **Tip 73 — "Apply Security Patches Quickly"** — Deferring known-vulnerability patches is indefensible; the largest breaches in history were behind-on-updates systems.
- **Tip 74 — "Name Well; Rename When Needed"** — Names reveal intent; a name that no longer fits its thing is a broken window — fix it now while you have the tests to catch misses.

## Ponytail relevance

### Listen before writing (Tip 61)
When code is "fighting back" — requiring more effort than it should — the book frames this as your lizard brain sensing that the design or problem statement is wrong. The right response is to stop, prototype, and reconsider, not to soldier on. **Supports laziness**: the code that doesn't need to exist is the code you almost wrote before your instincts stopped you.

### Don't rely on accidents (Tip 62)
"Don't assume it, prove it." Code built on undocumented behavior, copy-pasted context assumptions, or phantom patterns accumulates invisible debt that explodes later. Programming deliberately — understanding *why* something works — is the only way to keep code minimal and correctible. **Guardrail**: lazy code built on coincidence is unfinished, fragile code.

### Refactor continuously, not catastrophically (Tip 65)
The book's gardening metaphor: small, constant pruning beats the scorched-earth rewrite. "Fail to refactor now, and there'll be a far greater time investment to fix the problem down the road." Every addition of new code is an opportunity to clean up what was just written. **Supports laziness**: the effort deferred compounds; early refactoring keeps total code mass down.

### Testing is thinking, not overhead (Tips 66–69)
The chapter's central claim: "the major benefits of testing happen when you think about and write the tests, not when you run them." Thinking about how to test before writing the function reduces coupling, clarifies the API, and surfaces ambiguous requirements — all before a line of production code exists. The book also explicitly warns against TDD excess: redundant tests, inordinate pursuit of 100% coverage, and designs driven bottom-up by test structure rather than by destination. **Guardrail for non-trivial logic; tension if taken to TDD extremes.**

### Simple code is secure code (Tip 72)
"Code complexity makes the attack surface larger... Simpler, tighter, less complex code is easier to reason about, easier to spot potential weaknesses." Security and laziness point in the same direction: less code, fewer attack vectors. Never roll your own crypto — use well-vetted libraries. **Supports laziness** (do less, build on vetted code) and is simultaneously a **guardrail** (don't skip input sanitization or privilege minimization).

### Name things honestly, rename aggressively (Tip 74)
A name that no longer matches intent is "a broken window." The cost of a wrong name compounds as new developers internalize the lie. Modern IDEs make renaming cheap; the only excuse not to is coupling that should itself be fixed first. **Guardrail**: lazy naming that defers the decision creates maintenance debt that exceeds the original saving.

### Best isn't always fastest; premature optimization is waste (Topic 39 prose)
"Be wary of premature optimization. It's always a good idea to make sure an algorithm really is a bottleneck before investing your precious time trying to improve it." The Big-O analysis exists to catch *obviously* wrong choices, not to justify over-engineering. **Supports laziness**: do the simple thing, profile, then act.
