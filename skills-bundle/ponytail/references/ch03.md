# Chapter 03: The Basic Tools

> Master a small set of sharp, composable tools — shell, editor, VCS, text manipulation — until they become extensions of your hands.

## Tips in this chapter

- **Tip 25 — "Keep Knowledge in Plain Text"** — Store data in human-readable, self-describing form so every tool can reach it and it outlives any application.
- **Tip 26 — "Use the Power of Command Shells"** — The shell lets you compose tools in ways their authors never imagined; GUI limits you to what its designer intended.
- **Tip 27 — "Achieve Editor Fluency"** — Eliminate the mechanical overhead of editing so thought flows directly into the buffer without conscious friction.
- **Tip 28 — "Always Use Version Control"** — Everything goes in VCS: code, docs, config, scripts — even personal notes. No exceptions.
- **Tip 29 — "Fix the Problem, Not the Blame"** — Concentrate on repairing the defect; assigning fault wastes time that fixing requires.
- **Tip 30 — "Don't Panic"** — Step back, think about what could cause the symptoms; panic prevents clear diagnosis.
- **Tip 31 — "Failing Test Before Fixing Code"** — Write a test that reproduces the bug first; the act of isolating it often reveals the fix.
- **Tip 32 — "Read the Damn Error Message"** — The error message is the first clue; read it before reaching for the code.
- **Tip 33 — "'select' Isn't Broken"** — Assume the bug is in your code, not the OS or library; eliminate your code before blaming the platform.
- **Tip 34 — "Don't Assume It — Prove It"** — When a "bulletproof" routine surprises you, test it in this context, with this data, with these boundary conditions.
- **Tip 35 — "Learn a Text Manipulation Language"** — A scripting language (Python, Ruby, awk/sed) shrinks a multi-hour task to thirty minutes and makes experimentation cheap.

## Ponytail relevance

### Plain text as the minimum viable format (SUPPORTS)
Binary formats couple data to the application that wrote them; plain text is self-describing and readable by every tool that exists or will exist. The chapter argues that plain text "will outlive all other forms of data and the applications that created them." Choosing plain text for configs, test data, and logs is the laziest durable decision: no special parser, no migration tool, just grep.

### Shell composition over bespoke tooling (SUPPORTS)
"GUI environments are normally limited to the capabilities that their designers intended." The shell exposes the full repertoire of composable tools; a one-liner with pipes replaces a purpose-built utility. Building that utility instead would violate YAGNI and add maintenance burden.

### Editor fluency reduces invisible waste (SUPPORTS)
Fluency is not about learning every command; it is about noticing repetitive motions and eliminating them. "Every time you find yourself doing something repetitive, get into the habit of thinking 'there must be a better way.' Then find it." The payoff is that mechanics disappear and thought flows directly to output — a compounding laziness multiplier.

### Always use version control (GUARDRAIL)
Tip 28 is non-negotiable and absolute: "Always. Even if you are a single-person team on a one-week project. Even if it's a 'throw-away' prototype." VCS is the undo key that makes every other shortcut safe. Skipping it to save setup time is the careless kind of lazy.

### Failing test before fixing code (GUARDRAIL)
Tip 31 mandates a reproducing test *before* touching the code. "The act of writing the test informs the solution." This is a direct instance of ponytail's rule: non-trivial logic leaves one runnable check behind; a bug fix is non-trivial logic by definition.

### Prove it — don't assume (GUARDRAIL)
Tip 34 says: when a surprise failure appears, "Don't gloss over a routine or piece of code involved in the bug because you 'know' it works. Prove it. Prove it in this context, with this data, with these boundary conditions." Confidence without evidence is not laziness; it is debt.

### Invest in tool mastery up front (TENSION)
Learning shell idioms, editor key sequences, and a text manipulation language all require deliberate upfront effort that pays back over months, not immediately. This pulls against pure do-the-minimum-now laziness, but the book frames it as the efficient choice at career timescale: "Let need drive your acquisitions."

## Sharpest lines

- "The disadvantage is WYSIAYG — what you see is all you get."
- "Always. Even if you are a single-person team on a one-week project. Even if it's a 'throw-away' prototype."
- "If you 'changed only one thing' and the system stopped working, that one thing was likely to be responsible, directly or indirectly, no matter how farfetched it seems."
- "Spending 30 minutes trying out a crazy idea is a whole lot better than spending five hours."
