# Chapter 02: A Pragmatic Approach

> Every design principle in software reduces to one thing: make the system easier to change (ETC), and DRY, orthogonality, reversibility, and tracer bullets are all expressions of that single value.

## Tips in this chapter

- **Tip 14 — "Good Design Is Easier to Change Than Bad Design"** — ETC is the root principle; every other design heuristic is a special case of it.
- **Tip 15 — "DRY—Don't Repeat Yourself"** — Every piece of knowledge must have a single, unambiguous, authoritative representation in a system; duplication of _knowledge_ (not just code) creates maintenance nightmares.
- **Tip 16 — "Make It Easy to Reuse"** — Foster an environment where finding and reusing existing things is easier than writing them yourself; if reuse is hard, people won't do it.
- **Tip 17 — "Eliminate Effects Between Unrelated Things"** — Design self-contained, cohesive components whose changes don't ripple into unrelated parts of the system.
- **Tip 18 — "There Are No Final Decisions"** — No architectural decision is cast in stone; design so choices can be reversed cheaply.
- **Tip 19 — "Forgo Following Fads"** — Enable code to adapt to change rather than betting on any one current trend.
- **Tip 20 — "Use Tracer Bullets to Find the Target"** — Build a thin, end-to-end slice of the real system early to get immediate, real-world feedback; adjust aim before filling in detail.
- **Tip 21 — "Prototype to Learn"** — The value of a prototype is the lessons learned, not the code produced; throw it away afterwards.
- **Tip 22 — "Program Close to the Problem Domain"** — Write code using the vocabulary of the application domain; prefer off-the-shelf external languages (YAML, JSON) over rolling your own DSL.
- **Tip 23 — "Estimate to Avoid Surprises"** — Develop intuition for magnitudes so you can quickly distinguish feasible from infeasible before committing effort.
- **Tip 24 — "Iterate the Schedule with the Code"** — Refine estimates iteratively as you gain real experience on the project rather than locking in a single up-front number.

## Ponytail relevance

### ETC: one principle to rule them all (supports)
Every design guideline the book offers — decoupling, single responsibility, good naming — is justified as a special case of "easier to change." This aligns directly with the ponytail preference for boring, minimal designs: the simplest code is almost always the easiest to change. The authors frame ETC as a _value_, not a rule, floating behind decisions rather than demanding a checklist.

### DRY is about knowledge, not lines of code (guardrail)
"DRY is about the duplication of knowledge, of intent." Two functions with identical bodies may not be a DRY violation if they represent different facts that happen to coincide today. Conversely, a comment that restates what readable code already says _is_ a DRY violation. Ponytail's "delete over add" instinct must be checked here: collapsing distinct knowledge into one place to save lines is careless, not lazy.

### Orthogonality multiplies productivity (supports)
"An orthogonal approach also promotes reuse. If components have specific, well-defined responsibilities, they can be combined with new components in ways that were not envisioned by their original implementors." Isolated components are also cheaper to test and replace. Write shy code; avoid global data. This is pure ponytail: small, self-contained things you can forget about once they work.

### Reversibility: don't carve decisions in stone (supports)
The chapter argues that each irreversible commitment narrows the target until any environmental shift causes a miss. The antidote — DRY, decoupling, external configuration — is also ponytail's antidote. "Hide third-party APIs behind your own abstraction layers" at the boundaries; resist big-bang architecture commitments for the same reason you resist big-bang code.

### Tracer bullets vs. prototypes (guardrail)
"Prototyping generates disposable code. Tracer code is lean but complete, and forms part of the skeleton of the final system." Prototypes skip error checking and robustness intentionally. Tracer code does not. The distinction matters for ponytail: cutting corners on production-bound tracer code is careless; building disposable exploratory code to full production quality is wasteful. Know which you are writing.

### Domain languages: don't spend more than you save (tension)
Tip 22 says to program close to the problem domain, but the chapter immediately warns: "don't spend more effort than you save. Writing a domain language adds some cost." Prefer off-the-shelf external languages (YAML, JSON, CSV) before rolling an internal DSL; reach for metaprogramming only when users of the app will write in that language. This is a mild tension — the tip sounds ambitious but the body text is thoroughly YAGNI.

### Estimating: iterate, don't guess once (guardrail)
"Iterate the schedule with the code." Single up-front estimates on unfamiliar work are guesses; incremental estimation from actual experience is how to avoid the hidden cost of being wrong. Ponytail's laziness doesn't mean skipping the estimate — it means not padding an estimate to feel safe, and not betting on a grand plan that must be right the first time.

## Sharpest lines

- "Every piece of knowledge must have a single, unambiguous, authoritative representation within a system."
- "DRY is about the duplication of knowledge, of intent. It's about expressing the same thing in two different places, possibly in two totally different ways."
- "Prototyping generates disposable code. Tracer code is lean but complete, and forms part of the skeleton of the final system."
- "Don't spend more effort than you save." (on domain languages)
