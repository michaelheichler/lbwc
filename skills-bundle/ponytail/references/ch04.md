# Chapter 04: Pragmatic Paranoia

> Build defenses against your own mistakes: use contracts, crash early, assert assumptions, balance resources, and take only steps small enough to see by.

## Tips in this chapter

- **Tip 36 — "You Can't Write Perfect Software"** — Accept imperfection as an axiom; it frees you to build real defenses instead of chasing an impossible dream.
- **Tip 37 — "Design with Contracts"** — Document and enforce what every routine requires and guarantees; be strict in what you accept and promise as little as possible in return.
- **Tip 38 — "Crash Early"** — When something impossible happens, stop immediately; a dead program does far less damage than a crippled one writing corrupted data.
- **Tip 39 — "Use Assertions to Prevent the Impossible"** — Whenever you think "that can never happen," add code to check it; leave assertions on in production.
- **Tip 40 — "Finish What You Start"** — The function or object that allocates a resource should be responsible for deallocating it.
- **Tip 41 — "Act Locally"** — Reduce scope to the minimum needed; scoped lifetimes make release automatic and remove shared-state bugs.
- **Tip 42 — "Take Small Steps — Always"** — Let the rate of feedback be your speed limit; never take on a task that requires fortune-telling.
- **Tip 43 — "Avoid Fortune-Telling"** — Don't design for futures you can't see; design code to be replaceable instead.

## Ponytail relevance

### Contracts over defensive duplication (SUPPORTS)
DBC is explicitly framed as lazier than defensive programming: "DBC is more efficient (and DRY-er) than defensive programming, where everyone has to validate data in case no one else does." Specify preconditions and postconditions once at the boundary; callers and callees each do their own job, nothing more. The book also frames it as "lazy code: be strict in what you will accept before you begin, and promise as little as possible in return."

### Crash early, not elaborate recovery (SUPPORTS)
Propagating an exception with zero ceremony (`add_score_to_board(score)` versus three nested rescue blocks) is the lazier and more correct choice. The book shows that catch-and-reraise couples your code to every exception the callee might ever raise; letting it propagate is both less code and more future-proof.

### Scope is cleanup (SUPPORTS)
Tip 41 and the resource-balancing section push toward the smallest possible scope: "when in doubt, it always pays to reduce scope." Language-level scoped lifetimes (Rust, Ruby blocks, C++ destructors) beat manual cleanup code every time. Less code, no leak.

### Assertions are guardrails, not debugging scaffolding (GUARDRAIL)
"Turning off assertions when you deliver a program to production is like crossing a high wire without a net because you once made it across in practice." The chapter is explicit: assertions belong in production. This is the "not careless" half of laziness — the minimum check that proves non-trivial logic still holds.

### Small steps as anti-speculation (SUPPORTS + GUARDRAIL)
Tip 42/43 directly attack over-engineering: don't plan for futures you can't see, don't design for extendability beyond your headlights. Instead, "design your code to be replaceable." This is YAGNI in temporal form — the chapter names fortune-telling as a cost, not a virtue.

### Finish what you start (GUARDRAIL)
Resource balance (Tip 40) is non-negotiable: whoever allocates must deallocate, in consistent order, deallocated in reverse. Failing here causes data loss and resource exhaustion — exactly the "not careless" category ponytail never cuts.

## Sharpest lines

- "Be strict in what you will accept before you begin, and promise as little as possible in return. Remember, if your contract indicates that you'll accept anything and promise the world in return, then you've got a lot of code to write!"
- "A dead program normally does a lot less damage than a crippled one."
- "Turning off assertions when you deliver a program to production is like crossing a high wire without a net because you once made it across in practice."
- "Instead of wasting effort designing for an uncertain future, you can always fall back on designing your code to be replaceable."
