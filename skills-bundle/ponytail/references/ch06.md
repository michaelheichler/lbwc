# Chapter 06: Concurrency

> Concurrency is unavoidable in real systems; the safest way to handle it is to eliminate shared mutable state rather than manage it with locks.

## Tips in this chapter

- **Tip 56 -- "Analyze Workflow to Improve Concurrency"** -- Map your actual dependencies (activity diagrams work well) so you can spot steps that are serialized by habit rather than necessity.
- **Tip 57 -- "Shared State Is Incorrect State"** -- Any mutable resource touched by more than one thread is a latent bug; the right fix is architectural, not just a bigger lock.
- **Tip 58 -- "Random Failures Are Often Concurrency Issues"** -- Flaky, non-reproducible failures are a diagnostic signal pointing at unprotected shared state.
- **Tip 59 -- "Use Actors For Concurrency Without Shared State"** -- Actors hold private state and communicate only via messages, removing the need for locks entirely.
- **Tip 60 -- "Use Blackboards to Coordinate Workflow"** -- A shared event store lets independent agents contribute results in any order without knowing about each other.

## Ponytail relevance

### Temporal coupling is hidden complexity -- cut it (supports)
Sequential "do this, then that" code imposes ordering constraints that often don't exist in the problem domain. The book calls this *temporal coupling*: the code demands tick-before-tock even when tock doesn't actually depend on tick. Breaking temporal coupling is a deletion -- you remove an artificial constraint -- which is the laziest possible move.

### Shared state is not "just a mutex away" (guardrail)
The pie-case example shows that protecting shared mutable state correctly requires semaphores, exception-safe unlock, and transactional APIs -- and even then multi-resource scenarios cascade badly. The book's conclusion: "concurrency in a shared resource environment is difficult, and managing it yourself is fraught with challenges." A lazy dev who reaches for a quick mutex and calls it done is being careless, not efficient.

### Actors: zero synchronization code by design (supports)
The actor model eliminates shared state structurally. "There's no need to write any code to handle concurrency, as there is no shared state." No lock code written means no lock code to get wrong. This is YAGNI applied to synchronization primitives.

### Blackboards: decouple by ignoring each other (supports)
Blackboard/event-log systems let agents post results and subscribe to facts without knowing who else is listening. The book notes modern message brokers (Kafka, NATS) give this for free. Using an already-installed platform primitive instead of building a coordination layer is the ponytail default.

### Actor/blackboard architectures carry their own complexity (tension)
The book is explicit: "these approaches are harder to reason about, because a lot of the action is indirect." Distributed message tracing, central schema repos, and operational overhead are all real costs. Reaching for an actor framework when a simple synchronous call would work is over-engineering; the model is right only when concurrency is genuinely required.

### Random failures demand diagnosis, not retry (guardrail)
Tip 58 warns that non-reproducible failures are concurrency bugs in disguise. Wrapping them in retry loops or ignoring them is careless; the lazy senior dev finds the shared mutable resource and removes or protects it.

## Sharpest lines

- "Shared State Is Incorrect State" -- the tip title, blunt enough to stand alone.
- "Doctor, it hurts when I do this. Then don't do that." -- on managing shared-memory concurrency manually.
- "There's no need to write any code to handle concurrency, as there is no shared state." -- on the actor model.
- "Random Failures Are Often Concurrency Issues" -- the diagnostic heuristic worth internalizing before reaching for a sleep-and-retry.
